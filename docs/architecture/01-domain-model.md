# 01 — Domain model

**Status:** draft · **Supersedes:** [original proposal](../review/2026-08-original-proposal.md) §5 · **Resolves:** [M1](../review/2026-08-architecture-review.md#m1--terminology-drifts-between-synonyms), [M8](../review/2026-08-architecture-review.md#m8--malformed-glossary-table)

**Built:** Normative vocabulary — in force wherever the code names these things — see [implementation status](../implementation-status.md).

---

This document is **normative for terminology**. Where any other document, code identifier, log message, or user-facing string names one of these concepts, it uses the term defined here. The original proposal used two names for several concepts; that is a defect for a format intended to be implemented by third parties, and it is closed here.

## 1. Glossary

| Term | Meaning |
|------|---------|
| **Device** | A cryptographically identified FallbackPlan installation. Holds a keypair; the keypair is not derivable from the repository. |
| **Source** | A device together with the filesystem roots whose state it captures. |
| **Backup set** | A named unit of policy: source selection, exclusions, schedule, retention, destinations, and format profiles. |
| **Selection filter** | An include rule ([ADR-0024](../adr/0024-include-exclude-rule-dialect.md)), as the console names it where a new set's folders are chosen ([ADR-0037](../adr/0037-configuration-over-the-command-contract.md) Amendment 2). With none, a set captures everything under its roots; with any, only what matches one, and everything inside a folder that matches. An exclusion, whether an exclude rule or an unticked folder, always wins over it. |
| **Snapshot** | An immutable point-in-time representation of a backup set. |
| **Protection state** | A backup set's derived status — the closed vocabulary and its console glance layer are normative at [10 §1.1](10-observability.md#11-states-must-be-distinguishable). |
| **Repository** | The logical collection of encrypted content, metadata, indexes, and snapshots, identified by a repository ID. |
| **Store** | Physical object storage holding repository objects — a local directory, a peer, or a cloud bucket/container. |
| **Replica** | A store holding a copy of a repository's objects. A destination's replica is **whole-archive**: complete, self-verifying, independently restorable. It may lawfully lag the source or hold a hub-trimmed subset under retention; it never diverges ([ADR-0034](../adr/0034-hub-and-spoke-destinations.md)). |
| **Destination** | A named place a backup set replicates to, declared once in the client configuration and referenced by name from sets: a directory on a local or removable drive (`local-path`), a paired peer (`peer`), a bucket at a store that speaks the S3 API (`s3`, [ADR-0091](../adr/0091-an-s3-compatible-destination.md)), a container in a storage account that speaks the Azure Blob API (`azure-blob`, [ADR-0093](../adr/0093-an-azure-blob-destination.md)), or — schema-accepted now, implemented later — another cloud store. Holds a whole, independently restorable repository for each set that ships there — a staging set's destinations receive it as a replica of the staging archive by fan-out; a direct-ship set's receive it directly through the ship sink ([ADR-0046](../adr/0046-direct-to-destination-publication.md)). None of a set's destinations has to be local. |
| **Access key** | The credential an `s3` destination's requests are signed with: an id the store sees on every request, and a secret that signs and is never sent. The service alone holds it, owner-only in its state directory; it arrives sealed to the service for one destination and key id, and nothing says it back ([ADR-0091](../adr/0091-an-s3-compatible-destination.md)). Not a key of the repository's: it opens nothing, and reaches only the bucket. |
| **Object store** | A destination the service reaches through a store's own API rather than a filesystem or the peer protocol: an `s3` bucket or an `azure-blob` container. Every routine that serves one serves the other, and asks whether a destination is an object store, never which ([ADR-0093](../adr/0093-an-azure-blob-destination.md)). A run never writes through one; the sync after the run fills it. |
| **Account key** | The credential that signs an `azure-blob` destination's requests under the API's Shared Key scheme, and is never sent. It is the storage account's own, so it reaches every container in the account and does not lapse. Held and delivered as an access key is ([ADR-0093](../adr/0093-an-azure-blob-destination.md)). |
| **Shared access signature** | The other credential an `azure-blob` destination accepts: a token issued for one container, with the permissions and the expiry its issuer chose, sent with every request as it was issued. The service reads the expiry from the token, reports it, and sends nothing under a signature past it ([ADR-0093](../adr/0093-an-azure-blob-destination.md)). |
| **Hub** | The service instance on a user's machine, in its orchestrating role: it manages the machine's backup sets, plans retention for every destination, and holds each set's repository seat — a staging archive it fans out from (unflagged sets), or a metadata store it ships through the sink from (direct-ship sets). |
| **Spoke** | A destination, viewed from its hub. A spoke that is a peer runs its own FallbackPlan service and is a hub for its own sets; the roles are per-relationship, not per-installation. |
| **Staging archive** | The per-set repository archive on the hub where an *unflagged* set's publication lands. Internal — a cache the hub manages, not a destination a user configures or a policy counts. What makes a staging set's capture unconditional and fan-out a copy of sealed objects. A direct-ship set has none, and consciously trades the unconditional capture away ([ADR-0046](../adr/0046-direct-to-destination-publication.md) §4); a migrated set's leftover archive is a read-only seed source until `retire_staging` deletes it. |
| **Segment** | A logical portion of a file's byte stream, produced by the backup set's segmentation profile. |
| **Segment record** | The stored form of one segment: compressed, independently encrypted, independently authenticated. |
| **Blob** | An immutable physical container holding many segment or metadata records, plus a recovery footer. |
| **Merkle commitment** | A blob's second commitment, beside its flat digest and over the same bytes: an RFC 6962 tree of one-mebibyte leaves whose published root also binds the preimage's length ([ADR-0065](../adr/0065-merkle-commitment-and-chunk-possession.md), [05 §5.2](../../specifications/repository-format/05-blob.md#52-the-merkle-commitment)). Published as an index-delta key by a **format v3** writer only. What it buys over the digest is a check by a party holding neither the blob nor any key: one leaf and its authentication path settle whether that leaf is held. The **leaf's bytes** are the proof; the path is public arithmetic the examined party may cache. |
| **Format v3** | The repository format in which a sealed record stops encoding where it lives: its key is derived from the object rather than the blob, its nonce is drawn per record and carried in the record, and its associated data names no position — so the sealed bytes can be copied into another blob and still open ([ADR-0052](../adr/0052-relocatable-records-format-v3.md)). What the product creates ([ADR-0066](../adr/0066-the-format-upgrade-record.md)); format 2 remains creatable on request (`init --format-version 2`) and readable for ever. A repository created at a version declares it through a required descriptor feature, so a reader that does not implement it refuses by name. Note that a repository's version and the version stamped on one of its blobs are different numbers — see `Domain/FormatVersions`. |
| **Format-upgrade record** | The signed, append-only object under `format-upgrade/` by which a repository states that it writes a newer format from its next sealed object onward ([ADR-0066](../adr/0066-the-format-upgrade-record.md), [repository-format 11 §5](../../specifications/repository-format/11-lifecycle-objects.md#5-format-upgrade-record)). It exists because the descriptor cannot be rewritten in place — no copy path will replace it — and it is signed under the repository's signing key, since an upgrade changes what the writer emits and destroys nothing. |
| **Effective format version** | The format a repository **writes**: the highest version named by a format-upgrade record whose signature verifies, or the descriptor's own when there is none. The descriptor keeps the version the repository was **created** at, so the two are different questions and are reported separately where they differ. Fixed when an archive is opened, which is why the upgrade verb drops the open handle. |
| **Compaction backlog** | The blobs a collection pass keeps whole for a live minority: reachable from a protected snapshot in some part, mostly dead in the rest. The planner names them rather than counting them, and a pass rewrites the ones past a stated dead fraction, a reclaim floor and a per-pass byte budget ([ADR-0067](../adr/0067-the-keyless-compactor.md)). A **format v3** property: at format 2 the rewrite would need a content key the service does not hold. |
| **Drained blob** | A compaction candidate whose live records have been written into a new blob and whose index entries have been superseded. Nothing deletes it in the act: the collector condemns it on a later pass, because every record it holds now resolves elsewhere, and it is then tombstoned, graced and swept like any other garbage. |
| **Object identifier** | The keyed, repository-scoped identifier under which a record or manifest is referenced. See [`03-crypto.md` §4](03-crypto.md#4-object-identifiers). |
| **Content identifier** | The plaintext cryptographic hash of a segment. Used for deduplication and verification inside the trust boundary; never exposed to a store. |
| **File-version manifest** | An immutable object describing one version of one file: metadata, logical length, ordered segment references, whole-file hash. |
| **Sparse extent** | A range of a file recorded as a hole: an offset and a length that read as zeroes, stored as nothing ([specification 09 §4](../../specifications/repository-format/09-segmentation.md#4-sparse-extents)). The whole-file hash covers its zeroes. A restore skips it rather than writing it, so it stays a hole wherever the target filesystem can hold one and reads as zeroes everywhere ([ADR-0079](../adr/0079-sparse-restore.md)). Capture records extents on POSIX, where the filesystem reports its holes; an NTFS sparse file is read as data. |
| **Tree** | An immutable directory object referencing child trees and file-version manifests. |
| **Snapshot manifest** | The immutable root descriptor of a snapshot: source, backup set, capture details, root tree, policy, publication generation. |
| **Index delta** | An immutable, writer-authored mapping from object identifiers to physical locations, published after the blobs it covers are durable. |
| **Source-identity hint** | An advisory record naming the filesystem identity a new file version was captured from, so a later run can recognise a renamed or moved file as the same file ([specification 06 §11](../../specifications/repository-format/06-manifests.md#11-source-identity)). A publication writes the hints of every version it created as one **source-identity pack**, after its last content byte and before its snapshot record ([06 §11.5](../../specifications/repository-format/06-manifests.md#115-the-pack), [ADR-0090](../adr/0090-a-backups-hints-are-one-pack.md)). Earlier publications wrote one object per version, and those are still read. Never evidence; a run's finishing work is writing them ([ADR-0088](../adr/0088-a-backups-percentage-is-what-it-has-backed-up.md)). |
| **Checkpoint** | An immutable index generation that subsumes an explicitly enumerated set of deltas. |
| **Generation** | A monotonic marker of published repository index state. |
| **Catalogue** | The local, disposable, transactional database that materialises repository state for fast lookup. Never authoritative. |
| **Write intent** | A journal record published *before* a writer uploads blobs, naming the blobs it will create. Makes in-flight work reachable. See [`04-concurrency-and-publication.md` §4](04-concurrency-and-publication.md#4-write-intent). |
| **Blob counter reservation** | The blob counters — the writer numbers in blob identifiers — a publication allocates before it uses them, so a write intent can name blobs that do not exist yet. The intent names the first batch of eight, and when a batch runs out one intent extension names the next, twice the last up to 64, durable before the first blob numbered from it is uploaded. The intent's Completed retirement accounts for every number reserved, used or not, so a completed backup owes no void delta for one it did not use ([ADR-0092](../adr/0092-a-backup-names-its-blobs-a-batch-at-a-time.md)). |
| **Clock skew margin** | What a collector adds to a write intent's declared duration before the intent may expire, so a clock that disagrees with the writer's cannot cut a live job short: `clock_skew_margin_hours`, installation-wide in the configuration file, a day when absent ([ADR-0009](../adr/0009-garbage-collection-safety.md) Amendment 7). It binds only once the intent's generation has passed. |
| **Observed clock skew** | How far a machine's clock stood from a paired peer's, read from the `issued_at` the peer signs in a replication receipt against this machine's clock either side of that exchange, and good to half its round trip ([ADR-0077](../adr/0077-observed-clock-skew.md)). The peer's clock minus this one's, so positive means this clock was behind; named relative to the peer and never as slow or fast, because a disagreement does not say which clock is wrong. Each capture records the freshest reading, no older than a day, in its snapshot manifest (key 14), and records none — never 0 — when it has nothing to compare with. A diagnostic: nothing decides on it. |
| **Implausible capture time** | A snapshot's recorded capture time that does not fit the order its writer published it in, by more than the configured clock skew margin ([ADR-0078](../adr/0078-implausible-capture-times.md)). The yardstick is the longest run of the writer's snapshots whose times never fall as its publication sequence rises; where two runs are as long, the later times are taken as the truth. A snapshot off that run is *behind* when dated before the run's nearest member published ahead of it, and *ahead* when dated after the nearest one published after it. This machine's clock decides only which captures may anchor the run, and nothing is judged across writers or without a sequence. Retention keeps such a snapshot and never expires it: it fills no min-generations place and represents no bucket. |
| **Lease** | An advisory, time-limited coordination record. **Never** a correctness mechanism — see [`07-retention-and-gc.md` §4](07-retention-and-gc.md#4-why-leases-are-not-load-bearing). |
| **Tombstone** | A record marking an object as eligible for physical deletion after a grace period. |
| **Deletion request** | A person's ask that a snapshot go from staging and from every copy ([ADR-0080](../adr/0080-a-person-deletes-a-snapshot.md)): a tombstone of the snapshot's manifest with reason *requested* ([specification 11 §3.3](../../specifications/repository-format/11-lifecycle-objects.md#33-a-persons-request)), signed under the reclaim key. It is the request itself rather than a note of one, so every survey reads it and every plan expires the snapshot whatever its rules keep. Staging keeps the snapshot until every declared destination has converged since the request, which the sync ledger records as `converged_sequence`. The journal's audit record names who asked. |
| **Root** | The 32 bytes Argon2id derives from the passphrase and the descriptor's public salt and parameters; never stored, never wrapped, used only as the input to every other key's derivation ([spec 03 §2](../../specifications/repository-format/03-keys.md#2-the-root)). *Master key*, *key-encryption key (KEK)* and *key object* named format 1's stored, wrapped root; format 1 was withdrawn before any freeze and those terms no longer name anything on disk ([ADR-0014 Amendment 1](../adr/0014-format-versioning-and-stability.md#amendment-1-2026-09--format-1-withdrawn-before-freeze)). |
| **Write credential** | What a writing service holds: the structure root, signing root, content-ID key and key-ID key, plus the sealing, reclaim and claim *public* keys — every member an independent one-way HKDF domain of the root, so the whole credential yields neither the root nor any private authority ([ADR-0042](../adr/0042-write-only-repositories.md)). Stored by first-run setup for the installation, or per set by provisioning. Also *write bundle* in older records. |
| **Sealing key** | The X25519 keypair whose public half sits in the descriptor and whose private scalar exists only where the passphrase is present. Data-blob content keys seal to the public half; the descriptor's copy doubles as the wrong-passphrase verifier. |
| **Reclaim key** | The Ed25519 key that authorises *destruction* — tombstones, and retention instructions on the peer wire — derived per generation on a domain of its own, separate from the signing key that authorises publication ([ADR-0055](../adr/0055-reclaim-authority.md)). **Reclaim authority** is possession of it: a repository declaring the `reclaim-authority` feature acts on nothing destructive signed under any other key. A write-only service is deliberately not provisioned with it, so a service that may publish for ever cannot author a deletion; an ordinary service holds the master key and derives both, and there the retention floor is what holds instead ([07 §5](07-retention-and-gc.md#5-destructive-change-safeguards)). |
| **Claim key** | The Ed25519 key that proves a peer replica's *ownership* — derived from the **installation** (its passphrase and KDF salt) rather than from any one repository, because a machine claiming a replica has lost the repository and holds only the passphrase; the salt comes from the peer, which serves the KDF salts and costs behind its claimable replicas to a paired claimant ([ADR-0053](../adr/0053-peer-claim-and-configuration-recovery.md) Amendment 2). Not per generation, alone among the derived keys: a destination records the public half at first attribution and never replaces it, so a key that turned over would go stale with no way to say so. A **claim** is the ceremony that spends it — two phases in one session, the destination naming the derivations and the claimant answering one entry per derivation, all bound to the live session — and its effect is to re-point an attribution at the claimant's new device identity, granting no new power over the data. An attribution a claim moved is **held** — *awaiting acknowledgement* on the wire and in the ledger — until the destination's operator acknowledges the claim: the claimant reads at once and deletes nothing before then, because a passphrase can be stolen and the replica may be the last copy (FR-DR-005, [peer-protocol 07 §5.9](../../specifications/peer-protocol/07-retrieval.md#59-what-a-claim-does-and-does-not-carry)). |
| **Reclaim grant** | The reclaim sub-root sealed end-to-end to a write-only service's published recipient key and handed to it for one collection run, on the shape the restore grant already uses ([ADR-0042 §5](../adr/0042-write-only-repositories.md)). Zeroed with the run: a service compromised between runs holds nothing that deletes. One per set, derived by the client under the salt that set's archive records and proved against the reclaim public key its credential carries ([ADR-0055 Amendment 3](../adr/0055-reclaim-authority.md#amendment-3-2026-10--a-grant-per-set-from-every-client-proved-against-the-archives-key)). |
| **Deletion receipt** | A destination's signed statement of what it deleted on a retention instruction ([ADR-0063](../adr/0063-deletion-receipts.md)): the session the instruction arrived in, the commanding device, the floor and the reclaim key in force, a digest of each page as accepted, the keys removed and how many were never held — signed under the destination's own device key, since it holds no repository key, carried back in the `RetentionAck`, verified by the commander against the instruction it sent, and filed by both parties under `<state>/receipts/deletions`, where the `receipts` verb reads it. The peer plane's audit record beside the tombstone on the repository plane; it attests what the destination says it did, and possession stays verification's job. Kept under a stated rule (NFR-OPS-008): the newest 8 whatever their age, at most 4096 per repository, 365 days between the two. |
| **Replication receipt** | A destination's signed statement of what a push created and what its replica holds afterwards ([ADR-0064](../adr/0064-replication-receipts.md)): the session, the commanding device, the count and keys committed this session, and the objects and bytes held for the repository after it — signed under the destination's own device key, carried back in the `ReplicationAck`, verified by the commander against what it sent and what the inventory declared, and filed by both parties under `<state>/receipts/replications`. The one record on which the ledger counts a peer complete, as the peer's attestation and never as possession; read with the deletion receipts by `receipts`, `list_receipts` and the console's Receipts card. Kept for less than a deletion receipt — 8 / 1024 / 90 days — because one is issued on every push and each is superseded by the next. |
| **Recovery credential** | The passphrase — the one thing a person keeps that a recovery needs. Every archive's descriptor carries the rest (the KDF salt and parameters, the sealing public key that proves the passphrase, the repository id), so a recovery is the passphrase plus reach to an archive ([`08-restore-and-recovery.md` §4](08-restore-and-recovery.md#4-recovery-credential); [ADR-0060](../adr/0060-the-passphrase-is-the-recovery-credential.md)). |
| **Set shape** | What a configuration says about a backup set that its snapshot tree does not: the roots' source-machine paths and labels, the set's name and its schedule. Recorded on the policy manifest as optional keys ([06 §7](../../specifications/repository-format/06-manifests.md#7-policy-manifest)) so that an archive can re-declare the set that wrote it; **adoption** ([ADR-0061](../adr/0061-adopt-a-destinations-archives.md)) is the ceremony that reads it back — a rebuilt installation takes a destination's archive under its original repository and set ids with the passphrase, resumes the archive's writer identity when it safely can, and backs up incrementally into the same archive. Adoption is confirmed (FR-DR-009): its **preview** shows the recorded shape before anything takes effect, each root's recorded path flagged where it does not resolve on this machine, and answers a **confirmation** that adoption must carry. The set that takes effect is the one a person was shown. The set's own retention is recorded beside the shape since ADR-0061 Amendment 1; a destination's override, priority and destinations are not part of it. |
| **Recovery kit** | Withdrawn ([ADR-0060](../adr/0060-the-passphrase-is-the-recovery-credential.md)). The export that once made clean-machine recovery possible; for a format-2 installation its payload was a strict subset of every archive's descriptor, and the product no longer produces one. Older records that cite it are kept as written. |
| **Dedup trust domain** | The scope within which a device is willing to reuse another writer's segments. See [`03-crypto.md` §5](03-crypto.md#5-deduplication-trust-domains). |
| **Direct-ship set** | A backup set flagged `direct_ship` ([ADR-0046](../adr/0046-direct-to-destination-publication.md)): its content is written to its destinations directly through the ship sink, the agent holds metadata only, and a capture with no reachable destination refuses. The flag defaults off until its tail (the peer write adapter, the trimming drill) lands. |
| **Ship sink** | The `IObjectStore` a direct-ship set's publication writes (`DestinationShipSink`): `blobs/` route to the set's in-scope destinations and never to local disk; every other object routes to the metadata store *and* the destinations. Reads answer from whoever holds the bytes — metadata locally, blobs from the first destination in priority order, listings as the union. |
| **Metadata store** | A direct-ship set's local repository seat at `<state>/sets/<setId>/`: descriptor, keys, journal, index, snapshots, hints — everything except blob content. Carries the set's writer role and sequence; deliberately not an openable repository (the destinations are); rebuildable from any destination since they hold every object it does. |
| **Spool** | The per-set working buffer where blobs assemble before sealing and shipping ([`02-repository-format.md` §5.3](02-repository-format.md#53-spooling-and-sealing)). Not staging: a spool file lives from first record to the blob's last destination acknowledgement, bounded by in-flight blobs — a buffer, never a copy of the backup (ADR-0046 §5). |
| **Priority** | An optional integer on a set, a destination, or a set's destination reference ([ADR-0047](../adr/0047-backup-pool-and-priorities.md) §4). Orders waiting work beneath user-initiation — a person always outranks any priority — and orders which destinations a run ships to first. |
| **Baseline** | The fact that a destination holds a full backup of a set, recorded in the sync ledger as `baseline_completed_at`; a pair owed one is `needs_full` — skipped by incrementals and seeded by catch-up (ADR-0047 §§5–6, ADR-0046 §3). |
| **Backed up** | Of a running backup's counted plan, the logical bytes and the files whose content the store has acknowledged — for a direct-ship set, held at every destination the run writes to — or already held ([ADR-0088](../adr/0088-a-backups-percentage-is-what-it-has-backed-up.md)). Captured content counts in archive order once its blob and every earlier one have landed; an unchanged or renamed file counts the moment it is reused; a file that failed never counts. The files are the third of a job's three stages. |
| **Job stages** | A running backup's progress as three equal parts over its counted plan's files: scanned, processed, and backed up ([ADR-0088](../adr/0088-a-backups-percentage-is-what-it-has-backed-up.md) Amendment 1). What a job's bar shows, held at 99% until the snapshot is published; scanning has no total until it ends, so it has no percentage either. |
| **Files held** | Of a set's newest backup, the files whose content is all at one destination ([ADR-0088](../adr/0088-a-backups-percentage-is-what-it-has-backed-up.md) Amendment 1): what that destination's circle shows. Worked out from the ledger's watermark at rest and counted as content lands during a sync; while a run is live the console folds in what the run has stored or found unchanged. Not counted where nothing was ever delivered, and never 100% unless the destination holds the backup **whole**, its snapshot record included. The set's circle is its least complete destination's. |
| **Pause gate** | A run's cooperative suspension point ([ADR-0047 Amendment 1](../adr/0047-backup-pool-and-priorities.md#amendment-1--preemption-true-suspendresume-2026-08)): the capture pipeline checks it between scan events, so a parked run stops at a file boundary with its state held in memory and resumes without re-scanning. Two things ask for a park — a higher-priority arrival, and a **background window** closing over a running capture ([ADR-0069](../adr/0069-the-background-window.md)) — and each carries its own reason, because the reason is what the journal row a person reads the next morning says. A park that outlasts the max-pause bound self-cancels into the interruption-safe re-run path. |
| **Background window** | The hours background activity may start in, named installation-wide in the configuration file as `HH:mm-HH:mm` in local time and absent by default, which means always open ([ADR-0069](../adr/0069-the-background-window.md)). It governs exactly what the scheduler starts with nobody waiting — captures, fan-out syncs, replica sweeps and drills — and never a person: a restore, a manual run and `agent run --once` are ungated whatever the clock says. A window is a position on this machine's clock face rather than a span of instants, so a wrong clock mis-times a backup and never corrupts one. The first of NFR-PERF-013's four named limits to exist. |
| **Transfer limit** | A destination's byte rate, `transfer_limit` in the configuration file as a whole number and a binary unit per second, absent by default, which means unlimited ([ADR-0074](../adr/0074-background-byte-rate-limits.md)). It paces every byte background work moves to or from that destination, both ways — the fan-out's copy or push, a direct-ship run's writes, a sweep's and a drill's reads — through one limiter every such job shares, and never a person's work. The network half of NFR-PERF-013. |
| **Background read limit** | The rate background captures read their sources at, `background_read_limit` installation-wide in the configuration file and absent by default ([ADR-0074](../adr/0074-background-byte-rate-limits.md)); summed across the captures running at once, never applied to a person's run. The disk half of NFR-PERF-013. |
| **Service settings** | The installation's own settings — the background window, the background read limit and the backup pool's width (`max_concurrent_backups`) — as distinct from a set's or a destination's. Written in the configuration file and, since contract 1.44, read and set through the service ([ADR-0037](../adr/0037-configuration-over-the-command-contract.md) Amendment 1). The pool's width applies when the service next starts, so it has a stored value and a running one. The clock skew margin is an installation setting too, written only in the file ([ADR-0009](../adr/0009-garbage-collection-safety.md) Amendment 7). |
| **Rollback witness** | Whatever attests how far a writer had got when the writer's own allocation state cannot be trusted: at archive open, the repository's signed checkpoints, deltas and journal keys ([ADR-0008](../adr/0008-index-generations-and-checkpoints.md)); on a fan-out pass, the destination's journal keys for this writer, which are the one copy that outlives a state directory rolled back whole ([ADR-0062](../adr/0062-the-destination-is-the-rollback-witness.md)). A witness only ever raises the sequence. |
| **Verification tier** | Which proof a passed verification rests on, said beside the count (contract 1.32): a *comparison* against an independent copy, a record's *AEAD tag* opened at the destination, or the *digest* — the whole sealed blob hashed at the destination against the digest the writer signed into the index, the only proof a write-only set's data plane has ([ADR-0058](../adr/0058-peer-write-adapter.md) §8). |
| **Deep sweep** | The scheduled re-read of a replica's every stored blob against the digest sealed into its own footer ([ADR-0035](../adr/0035-destination-fitness.md) §4) — a local path's on its interval, a peer's over the retrieval session only on a cadence its source's operator states (Amendment 2), an S3-compatible store's over its API on the same terms ([ADR-0091](../adr/0091-an-s3-compatible-destination.md) Amendment 1). It reads in bounded runs that resume from a cursor — the record and the code call a run a *segment*, which has nothing to do with a content **segment** above — and one pass over every blob is a **circuit**. A circuit once begun is carried on every scheduler pass, and the destination's interval rests between circuits (Amendment 1). A segment that stops at a blob it could not read has **stalled**: what it read stands, and the next attempt waits the sync's back-off rather than the next pass. A stall is not a finding. Distinct from the sync-time challenge, which samples. |
| **Repair** | Replacing an object the deep sweep found damaged at a destination with a copy proven sound where it sits — its whole blob still hashing to its sealed digest, and its envelope naming the blob its key derives from — from the staging archive, another destination, or a peer's replica over the retrieval session ([ADR-0035](../adr/0035-destination-fitness.md) Amendment 1, FR-VER-007). Nothing at the destination is touched until a copy is proven, and with none the damaged object is kept. At an S3-compatible store the damaged object is deleted and the copy put in its place, since a put there never overwrites ([ADR-0091](../adr/0091-an-s3-compatible-destination.md) Amendment 1). Not *heal*, which names copying a destination's metadata back to a rolled-back hub ([ADR-0062](../adr/0062-the-destination-is-the-rollback-witness.md)). |
| **Restore drill** | Restoring a bounded sample of files out of one destination's own replica, opened as a stranger would open it, to prove that copy still restores ([ADR-0054](../adr/0054-scheduled-restore-drills.md), FR-DRL-002). It runs on a cadence, thirty days by default for a local path and only on a stated cadence for a peer, and whenever a person asks (FR-DRL-003). Its answer is recorded per (set, destination) pair as one of three states — never drilled, drilled and passed, drilled and failed — and a failure raises a notice without touching the pair's sync state. One drill of a pair runs at a time: an ask while it is being drilled joins the drill under way. Not a verification, which proves a copy holds authentic bytes; a drill proves the road from those bytes back to a file. |
| **Read around** | What a restore of a set's own archive does with a record its own store will not serve ([ADR-0075](../adr/0075-a-restore-reads-around-damage.md), FR-RST-007). It reads the same record — the same blob at the same offset, since blobs are immutable and a replica holds them byte for byte — from the set's next copy: its local-path destinations by priority, then its peers over the retrieval session, each opened only once every earlier one has failed. What it reads is verified as the first copy's would have been. A copy passed over is *damaged* (a finding, put on the destination's ledger row as the deep sweep's are), *unreadable* (not a finding), or does not hold the blob (a staging archive's trimmed history, which is routine). A restore from a destination named as its source reads that copy alone, because a drill proves that copy through it. |
| **Reach** | What damaged objects are needed by: the snapshots a restore of which would meet them, and the paths in those snapshots ([ADR-0076](../adr/0076-damage-is-traced-to-what-needs-it.md), FR-VER-005). Traced through the catalogue from a damaged blob to the objects a read would take from it, to the file versions that need them or are them, and so to the snapshots and paths holding those versions — or to the snapshot whose own records they are. Traced when it is asked for rather than kept from the finding, so a snapshot taken since that needs the same objects is in it. What nothing traces is counted and makes the reach incomplete, and an incomplete reach counts every snapshot as needing the damage. A pair failed for its damage alone degrades the snapshots in the reach and no others. |
| **Room** | What a restore needs on each volume it writes to, measured before it writes ([ADR-0083](../adr/0083-a-restore-says-whether-it-fits-and-what-it-will-not-write-back.md), FR-RST-003): each file's written bytes, its holes skipped, in whole 4 KiB clusters; a cluster for each directory it creates; and the largest file's *working space* where that shares the volume. In place, it is credited only what the existing-file policy frees. Measured against what the platform says is free; a platform that will not say is never short. A run short of room is refused before anything is written, unless the person chooses to restore anyway, because a volume that compresses what it stores holds more than the estimate. |
| **Working space** | Where the engine holds a file until its whole-file hash verifies, before the file is copied to where it lands: the system's temporary directory. A restore needs room there for its largest file, counted into the volume's own room when the two share one and stated apart when they do not ([ADR-0083](../adr/0083-a-restore-says-whether-it-fits-and-what-it-will-not-write-back.md)). A hole takes none of it ([ADR-0079](../adr/0079-sparse-restore.md)). |
| **Not applied** | A captured attribute a restore did not write back to an item it landed ([ADR-0083](../adr/0083-a-restore-says-whether-it-fits-and-what-it-will-not-write-back.md), FR-RST-004). The receipt names it per item, in the format's words (`created_at`, `owner`, …). The plan counts it per attribute beforehand, and the run's answer counts it afterwards. An item's outcome does not change for it: this is architecture 06 §3's *degrade and report*, never a silent drop. A restore applies a file's modification and access times, its creation time where the platform can set one, and on a POSIX target its owner and group where the *restoring account* may give them, then its extended attributes on Linux and macOS, then its POSIX mode; everything else captured is not applied yet. The receipt records what each write did, so a write the platform refuses is not applied too ([ADR-0084](../adr/0084-a-restore-writes-back-the-times-it-can-set.md)). An extended attribute the rule withholds or the volume refuses leaves `extended_attributes` not applied, and the item's detail names it and why ([ADR-0087](../adr/0087-a-restore-writes-back-the-extended-attributes-it-may.md)). A folder the restore makes is given the same, once everything in it has landed. A folder already at the destination keeps its own, so everything captured with it is not applied ([ADR-0086](../adr/0086-a-restore-gives-a-folder-its-own-metadata-back-last.md)). |
| **Restoring account** | The account a restore runs as, which decides whose files it may give away ([ADR-0085](../adr/0085-a-restore-gives-a-file-back-to-its-owner-where-it-may.md), FR-RST-004). A captured owner or group is a name, resolved on the target. It is given back where it resolves and the account may give it: root, or a Linux process holding CAP_CHOWN, may give a file to anyone; any other account only to itself and the groups it is in. The plan predicts each file by it, and says whether a name needs privilege or resolves to nothing. A set-id bit is kept only with the owner or group it runs as. On Linux only a restoring account that is root writes the security and trusted namespaces; any other leaves them, and its plan says so ([ADR-0087](../adr/0087-a-restore-writes-back-the-extended-attributes-it-may.md)). Windows has none, because its owner lives in the security descriptor. |
| **Captured here** | Whether the installation restoring a snapshot is the one that captured it: the device the snapshot names is its own ([ADR-0087](../adr/0087-a-restore-writes-back-the-extended-attributes-it-may.md), FR-RST-004). A Linux ACL names accounts by number, and a number names the account it meant only on the machine that captured it, so an ACL that names one is written back only where its snapshot was captured here; elsewhere it is not applied, and the file's group is given no more than the ACL gave it. The device a snapshot names is attribution by claim ([ADR-0020](../adr/0020-ed25519-signing-key-semantics.md)), so this guards an honest restore on another machine, not against a member of the repository who lies. |
| **Redacted rendering** | How a log record or a diagnostic bundle's field is written once it leaves the machine ([ADR-0043](../adr/0043-structured-logging-and-diagnostics.md) §4 as amended by [ADR-0081](../adr/0081-diagnostic-bundle.md)). Fail-closed: a value crosses only when its declared type says how — a path as a short digest, an identifier as a short prefix, a **label** (words a call site vouches for: the code's own vocabulary, or a name a person gave something) as written — and anything else, an exception's message included, is withheld. The service's own log file is not redacted; it never leaves. |
| **Diagnostic bundle** | One file a person can send to whoever is helping them: the service's log, versions, configuration, status, open notices and recent jobs, each in its redacted rendering ([10 §4](10-observability.md#4-diagnostics), [ADR-0081](../adr/0081-diagnostic-bundle.md)); or, from the standalone recovery tool, a report of one run — what the archive said, how far the run got and why it stopped — rendered by the same rule ([ADR-0082](../adr/0082-the-recovery-tools-diagnostic-bundle.md)). Never carries a credential, key or recovery material; carries plaintext paths only by an opt-in made for that bundle, which a paired console may not make. |
| **Passphrase gate** | The rule that a backup's file names reach a person only after they prove the set's passphrase for the look at hand ([ADR-0089](../adr/0089-a-backups-file-names-need-the-passphrase.md), FR-WOR-007): listing a snapshot, planning or running a restore, a run's changes and failures, and the files a notice leaves out, which its words count instead (Amendment 1). Nothing remembers a proof, so every look asks again. Names on disk now are not the backup's and are not gated. |
| **Unlocked source** | A restore source opened under a restore grant ([ADR-0042](../adr/0042-write-only-repositories.md) §5): the proof the passphrase gate asks for. It serves only the session that opened it and only its own set, and it is closed when the look it was opened for ends. The service's own drill opens a source without a grant; that source is not an unlocked one. |

## 2. Terms we do not use

Each of these appears in the prior art and in the original proposal. They are listed so readers arriving from another product can map their vocabulary — and so that reviewers can flag their reappearance in our own text.

| Do not use | Use instead | Where it comes from |
|------------|-------------|---------------------|
| chunk | **segment** | content-addressed snapshot repositories |
| block | **segment** | consumer peer backup services; file synchronisers |
| pack, pack file | **blob** | content-addressed snapshot repositories |
| volume, data file | **blob** | plugin-oriented backup clients |
| local database, local index | **catalogue** | products with an authoritative local database |
| lock | **lease** (advisory) or **write intent** (correctness) | content-addressed snapshot repositories |

Two qualifications. The rule governs **nouns**: *packing* is fine as a verb for the act of assembling records into a blob, and *content-defined chunking* keeps its established name because that is what the algorithm is called everywhere. Sections describing prior art may still use the source's own vocabulary where translating it would obscure the point being made — but they name the design, not the product ([naming and attribution](../naming-and-attribution.md)).

Note too that "blob" is overloaded in the wider ecosystem: Azure Blob Storage — an interface this project implements against, so its name stays — calls every stored object a blob. Where that ambiguity could bite — chiefly [`05-storage-providers.md`](05-storage-providers.md) — we say **repository blob** for ours and **store object** for the provider's unit of storage.

## 3. Object relationships

```text
Snapshot manifest
  ├── source device, backup set, capture window, policy ref, publication generation
  └── root tree
        ├── tree (subdirectory)
        │     └── … recursively
        └── file-version manifest
              ├── path identity, metadata, logical length, whole-file hash
              ├── parent file-version manifest (previous version, where known)
              └── ordered segment references
                    └── (logical offset, logical length, OBJECT IDENTIFIER)
                                                          │
                    ┌─────────────────────────────────────┘
                    │  resolved by the index, never by the manifest
                    v
              Index delta / checkpoint
                    └── object identifier → (blob, record offset, stored length, profiles)
                                              │
                                              v
                                            Blob
                                              ├── cleartext envelope (format, key generation, blob salt)
                                              ├── segment records (independently encrypted + authenticated)
                                              └── authenticated recovery footer (record table)
```

The indirection at the marked line is deliberate and load-bearing. A manifest states *what* a file is made of; the index states *where* those parts currently live. Because compaction moves records between blobs, physical location cannot live in an object that is declared immutable — this was the original proposal's most serious internal contradiction ([C1](../review/2026-08-architecture-review.md#c1--immutable-manifests-embed-physical-locations-that-compaction-changes)), and the separation above is what resolves it.

The blob recovery footer holds the same mapping the index does, which is what makes forensic rebuild possible when every index object has been lost.

## 4. Snapshot semantics

A snapshot manifest records:

- source device identity and backup-set identity;
- capture start and completion time;
- parent snapshot(s), where applicable;
- root tree object identifier;
- filesystem capabilities and case-sensitivity observed at the source;
- policy version and the effective format profiles used;
- consistency method — live scan, VSS, or filesystem snapshot;
- errors, unreadable paths, and partial-capture status;
- the **observed clock skew** — how far the source's clock stood from a peer's, where one was read (see [`04-concurrency-and-publication.md` §7](04-concurrency-and-publication.md#7-time-and-clock-skew));
- client and repository format versions;
- a signed declaration by the writing device.

Snapshots are never modified. Corrections create new declarations or administrative records; they never rewrite historical objects.

### 4.1 Commit is not replication

A snapshot is **committed** to a replica once every object it references is durable *in that replica*. Commit is a per-replica property and is always achievable locally.

**Replication** state — whether a given destination holds the snapshot, and whether that has been independently verified — is tracked separately, per `(snapshot, destination)` pair.

Conflating the two makes protection hostage to the least available destination: a peer switched off for a fortnight would block every snapshot, including the local one that is working perfectly ([C5](../review/2026-08-architecture-review.md#c5--snapshot-commit-is-defined-so-that-one-offline-destination-stalls-all-protection)). Full model in [`04-concurrency-and-publication.md` §6](04-concurrency-and-publication.md#6-commit-versus-replication).

## 5. Replication, not synchronisation

The first release replicates repository objects, not live source folders:

- a source scan produces a snapshot, published once — into the set's staging archive (unflagged sets), or through the ship sink to the set's reachable destinations directly (direct-ship sets, [ADR-0046](../adr/0046-direct-to-destination-publication.md));
- the snapshot references immutable trees, file-version manifests, and segments;
- missing immutable objects reach each of the set's destinations as they are available — by fan-out from staging, or by catch-up through the sink from whichever destination holds them — and the ones that were away are caught up;
- a snapshot commits to a replica once its referenced objects are durable there;
- a deletion appears in a later snapshot and erases nothing;
- retention selects which snapshots remain protected, per set and per destination;
- garbage collection removes unreachable objects only after safety checks and grace periods — marked by the hub, executed at each destination on its instruction.

This yields the transfer efficiency of synchronisation while preserving backup semantics.
