# Proof obligations

**Status:** maintained · **Checked by:** [`eng/check-proofs.py`](../eng/check-proofs.py)

---

This page states the invariants the product actually rests on, and for each
one says what would falsify it and what would catch that happening. It exists
because the 2026-09 architecture review asked for it, and because the two
registers either side of it answer different questions: the
[traceability matrix](requirements/traceability.md) maps *requirements* to
tests, and [implementation status](implementation-status.md) maps *decisions*
to code. Neither asks the question this one does — **if this claim were false,
what would go red?**

The difference matters most where the answer is "nothing". A requirement with
a test is traced; an invariant with no falsifier is a belief. Both registers
above would show the second as healthy, because nothing in them is wrong: the
requirement is met, the decision is built, and the property nobody thought to
attack is simply not represented. So the gaps are written into the table
rather than left out of it, each naming the requirement that would carry the
work, which is how a prose worry becomes something countable.

**Legend**

| State | Means |
|-------|-------|
| **Proved** | A named test or drill goes red if the invariant breaks |
| **Partly proved** | Part of the falsifier is exercised; the row names the part that is not |
| **Unproved** | The invariant is claimed and nothing here would catch its breach |
| **Open by decision** | The invariant does *not* hold, deliberately; the row names the record that decided it |

A **Proof** cell names test classes as `Project/ClassName`, or a file under
`eng/` for a drill. `eng/check-proofs.py` resolves every one of them and
refuses a build that cites a class nobody wrote — the lesson the traceability
matrix taught expensively, applied here before the same thing can happen
again. Every **Unproved** row must cite at least one requirement id, so a gap
cannot be recorded as a shrug.

## The obligations

### Writing

| Invariant | What would falsify it | Proof | State |
|-----------|-----------------------|-------|-------|
| A committed snapshot restores in full — every object it depends on is present and readable | Kill the writer after each persistence boundary in turn, then restore every snapshot that reported committed | `InterruptionTests/PublicationInterruptionTests`, `InterruptionTests/TreeSnapshotInterruptionTests`, `InterruptionTests/StoreFaultTests` | **Proved** (NFR-REL-001) |
| Interrupted blob construction never becomes visible as a committed object | Kill mid-blob, at each checkpoint and between them; then resume, and separately abandon | `InterruptionTests/BlobSpoolResumeTests`, `InterruptionTests/SpoolHygieneTests`, `InterruptionTests/VoidObligationTests` | **Proved** (FR-ARCH-011) |
| A blob identifier is never reused, whatever happens to the sequence file | Roll the durable sequence state back and re-run the writer | `InterruptionTests/SequenceRollbackTests`, `InterruptionTests/SequenceAccountingTests` | **Proved** (FR-SNP-006) |
| No `(key, nonce)` pair is ever assigned twice, in either construction | Crash, resume, restart and concurrent writers, collecting every pair assigned across all of them — and, for format 3, one object sealed many times, which is where a fixed nonce would fail and a dense-ordinal argument would not notice | `Repository.Tests/NonceUniquenessTests`, `Repository.Tests/BlobKeySeparationTests` | **Proved** (NFR-SEC-003) — two constructions, held together: format 2's pair is a per-blob derived key and a dense ordinal, separated by a fresh CSPRNG salt per blob; format 3's is an object-scoped key and a nonce drawn per record ([ADR-0052](adr/0052-relocatable-records-format-v3.md) Amendment 1, which withdrew the constant nonce the design first proposed — the object identifier is over the plaintext while the sealed bytes are the stored form, so one object can be sealed twice under one key with different bytes) |
| Memory is bounded by configuration, not by the size of the input | One synthetic file far larger than memory; measure peak RSS | `Repository.Tests/BoundedMemoryTests`, `PerformanceTests/MemoryBoundProof` | **Partly proved** — the scaling property is held at test scale for the capture pipeline, and spool resume is now held separately and directly by `Repository.Tests/SpoolCheckpointTests`, which refuses an allocation proportional to the spool's length. What is still unproved is the requirement as written: nothing gates peak RSS in CI, and no test processes anything near the 2 TiB the acceptance criterion names (FR-ARCH-002, NFR-PERF-001) |

### Reading back

|-----------|-----------------------|-------|-------|

| The passphrase and reach to the archive are sufficient — no catalogue, no local state, no kit, no this machine | Destroy the state directory, the catalogue and the source, then restore from the destination alone | `Repository.Tests/PassphraseDrillTests`, `Hosts.Tests/RecoveryHostTests`, `eng/recovery-drill.sh` | **Proved** (FR-DRL-001) — the standalone tool opens an archive from the passphrase and the archive's own descriptor, and `eng/recovery-drill.sh` runs that sequence against the Release binaries with the state directory destroyed and nothing saved beforehand ([ADR-0060](adr/0060-the-passphrase-is-the-recovery-credential.md)) |
| The catalogue is a cache and never an authority | Delete it; then delete the index plane as well and rebuild from blob footers | `Repository.Tests/CatalogueRebuildTests`, `Repository.Tests/ForensicRebuildTests`, `Repository.Tests/StaleCatalogueTests`, `Hosts.Tests/CatalogueRebuildAtOpenTests` | **Proved** (NFR-REL-002, NFR-REL-003) — and the service rebuilds a catalogue it finds deleted, or discarded for another schema, before it answers from it: until [ADR-0010 Amendment 4](adr/0010-local-store-separation.md#amendment-4-2026-09--a-catalogue-discarded-is-rebuilt-before-it-is-read) it did not, and a set whose catalogue had been discarded listed none of its snapshots |
| Corruption stays local: one damaged record does not cost the blob, one damaged blob does not cost the archive | Corrupt a record, a footer, a whole blob; fuzz every parser | `Repository.Tests/ArchiveCorruptionTests`, `InterruptionTests/CorruptionHarnessTests`, `Repository.FuzzTests/ParserFuzzTests` | **Proved** (FR-ARCH-009, NFR-REL-004) |
| Restore never writes outside the restore root | Offer a repository path that escapes it, in every spelling the platform allows | `Repository.Tests/RecoveryContainmentTests`, `Storage.ContractTests/LocalFileSystemSecurityTests` | **Proved** (FR-RST-005) |
| A restored file is the file that was captured, its holes holes again | Restore a sparse file through the engine, the service's executor and the recovery tool, and measure what each allocates; restore it into a destination that cannot seek, and into one that already holds bytes where it goes; capture a file that is one hole | `Repository.Tests/SparseRestoreTests`, `Domain.Tests/SparseFileTests` | **Proved** (FR-ARCH-013) — on the three filesystems CI restores onto, ext4, APFS and NTFS. A 98 MiB file holding 2 MiB of data between three 32 MiB holes comes back byte-identical and verifying. Measured after it is written back, it allocates no more than its data and half a hole, at the destination and in the engine's spool, so not one hole was filled. Every zero is written where a hole could not be left ([ADR-0079](adr/0079-sparse-restore.md)). Where a filesystem cannot hold a hole the zeroes are allocated, which specification 09 §4 makes the expected form. APFS cannot hold one shorter than 16 MiB, and fills it itself |
| A restore fetches what it needs and not what it holds | Let the read path's request count track repository size, file count or record count rather than the blobs the restore needs | `Repository.Tests/RestoreBreadthTests` | **Partly proved** (NFR-PERF-009, NFR-PERF-001) — the same whole-snapshot restore is 11 GETs over 11 blobs holding 60 records, against a budget of 14 and against 93 before ([ADR-0068](adr/0068-the-catalogue-directed-restore-read.md)), and the falsifier is held by scale rather than by a pinned count: the one-file case measures the same restore twice against a store that has grown several times over and must not have got dearer. The two halves that make the number possible are held separately, because each is losable on its own — a read that opens no footer, and coalescing under bounds that keep the saving from being paid for in bandwidth or memory. Nothing verifies differently for having arrived in a bigger read: a run that covers only part of a record is refused rather than served short, and the object-id cross-check — the whole of what stops a location pointing at a valid neighbour returning that neighbour's bytes under the requested object's name — is held on the coalesced path as well as the dedicated one. **Partly**, on the case the record names rather than absorbs: a sparse restore of one small record out of large blobs cannot fold the envelope into the run that fetches it, so it costs two reads a blob and stays over the budget |

| A repository moves to a newer format without rewriting anything it already holds, and every copy learns of it | Upgrade a set, then look at a destination after a reconciling pass — a copy still claiming the older format, or one that will not open, falsifies it; so does an upgraded set that goes on sealing the older format, or one that stops restoring what it wrote before | `Repository.Tests/FormatUpgradeRecordTests`, `Repository.Tests/EffectiveFormatTests`, `Hosts.Tests/FormatUpgradeTests` | **Proved** (FR-MAN-019, NFR-COMP-004) — an append-only signed record under `format-upgrade/`, not a rewritten descriptor, because a destination is seeded with the descriptor if absent, a peer keeps the copy it has and `repository-format` may not be named by a retention instruction, so a rewrite would move the source alone ([ADR-0066](adr/0066-the-format-upgrade-record.md)). The record rides every copy path with no protocol change, and is refused by name when an instruction names it for deletion. Two limits are stated rather than hidden: a destination holds newer blobs before it holds the record that explains them, until the next reconciling pass — which costs nothing, because every blob declares its own container — and a build older than the newer format meets it at that first blob, refusing as damage rather than by name |

### What leaves the machine

| Invariant | What would falsify it | Proof | State |
|-----------|-----------------------|-------|-------|
| Nothing leaves the device that nobody asked for | Put a default installation through its ordinary work and watch the process's own network instrumentation: a connect to an address on an IP network, a name resolution or an HTTP request falsifies it — and so, before any run, does a shipped assembly that could make one | `ArchitectureTests/TelemetrySilenceTests`, `Hosts.Tests/DefaultBuildSilenceTests` | **Partly proved** (NFR-PRIV-001) — proved in two halves that answer different questions. The build holds no **means**: no shipped assembly references an HTTP client, outbound capability is confined to the five that are the peer protocol and the loopback IPC, nothing attaches a `MeterListener` or an `ActivityListener` to the in-box instruments — the route that needs no package at all ([ADR-0027](adr/0027-services-scheduling-status-telemetry.md) §3) — and the twelve packages the product ships are pinned as a set, because an update check, a crash reporter and a usage beacon share no name, only the fact that somebody added a dependency. And a default **run** is captured: setup, a backup to a local path, status, snapshots, a restore and a retention pass, driven through the transport an operator's terminal uses, reaching no IP address and resolving no name. The capture is held honest by a positive control — the product's one legitimate outbound connection, a peer destination the operator configured, decoded back to the endpoint the configuration named — which earned its place at once: breaking the instrument left the silence assertion **passing** and only the liveness cases red. **Partly**, on the limit the halves exist to cover for each other: the capture observes this process, not the machine, so it is not a packet capture and cannot see a child process; what makes one observed run worth generalising from is a build that cannot reach the network and a package list that cannot grow in silence |

### Destinations and durability

| Invariant | What would falsify it | Proof | State |
|-----------|-----------------------|-------|-------|
| `verified` means bytes were read at the destination and checked against evidence it does not hold | Corrupt a blob at a set's only destination, and separately let a converged set sit with nothing to copy | `Hosts.Tests/DestinationVerificationTests`, `Hosts.Tests/DirectShipVerificationTests`, `Replication.Tests/ReplicaVerifierTests` | **Proved** — a peer answers a keyed range challenge; a readable destination has its sampled blobs *opened* at the replica, so the AEAD tag the writer computed is the evidence and no second copy is needed. | A protected historical piece stays provable after the source copy is discarded | Delete the source copy, then corrupt the destination's | `Hosts.Tests/DirectShipVerificationTests`, `Hosts.Tests/PeerReadBackVerificationTests`, `Replication.Tests/ReplicaVerifierTests`, `Repository.Tests/CatalogueTests` | **Proved** (FR-VER-001, FR-WOR-003) — a blob is proved by opening it at the replica, which needs no source copy at all, and the write-only data plane, whose records the service cannot open, is proved by the **digest tier**: the whole sealed blob hashed at the destination against the digest the writer signed into the index, which a rebuilt catalogue now keeps. ## How to use this

**When adding an invariant**, add the row before the code. The falsifier
column is the useful half: an invariant whose falsifier cannot be written down
is not yet stated precisely enough to be worth testing.

**When a row moves to Proved**, it moves because a named class goes red
without the code, not because the code looks right. A test that passes both
with and without the invariant is not a proof of it, and the checker cannot
tell the difference — that judgement is the reviewer's.

**When a row stays Unproved**, that is information, not a failure. Three of
the rows above are phase-4 work correctly not started. What the register
refuses is the fourth possibility: an invariant everyone assumes and nobody
has looked at.
