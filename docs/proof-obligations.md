# Proof obligations

**Status:** maintained · **Checked by:** [`eng/check-proofs.py`](../eng/check-proofs.py)

---

This page states the invariants the product actually rests on, and for each
one says what would falsify it and what would catch that happening. It exists
because the 2026-09 architecture review asked for it, and because the two
registers either side of it answer different questions: the
[traceability matrix](requirements/traceability.md) maps *requirements* to
tests, and [implementation status](implementation-status.md) maps *decisions*
to code. Neither asks the question this one does — **if this claim were false,
what would go red?**

The difference matters most where the answer is "nothing". A requirement with
a test is traced; an invariant with no falsifier is a belief. Both registers
above would show the second as healthy, because nothing in them is wrong: the
requirement is met, the decision is built, and the property nobody thought to
attack is simply not represented. So the gaps are written into the table
rather than left out of it, each naming the requirement that would carry the
work, which is how a prose worry becomes something countable.

**Legend**

| State | Means |
|-------|-------|
| **Proved** | A named test or drill goes red if the invariant breaks |
| **Partly proved** | Part of the falsifier is exercised; the row names the part that is not |
| **Unproved** | The invariant is claimed and nothing here would catch its breach |
| **Open by decision** | The invariant does *not* hold, deliberately; the row names the record that decided it |

A **Proof** cell names test classes as `Project/ClassName`, or a file under
`eng/` for a drill. `eng/check-proofs.py` resolves every one of them and
refuses a build that cites a class nobody wrote — the lesson the traceability
matrix taught expensively, applied here before the same thing can happen
again. Every **Unproved** row must cite at least one requirement id, so a gap
cannot be recorded as a shrug.

| Another writer's segment is confirmed against its plaintext before it is referenced | Publish a record whose claimed content identifier does not match its bytes, then back up against it | `Repository.Tests/DedupTrustDomainTests` | **Partly proved** — the gate itself holds in all three domains. | A sealed **format-3** record can be relocated between blobs without its key | Move a record into another blob — another salt, another writer, another derived blob key, another ordinal — and read it back with the same key material | `Repository.Tests/RelocatableBlobTests`, `Repository.ConformanceTests/FixtureRepositoryV3Tests` | **Proved** (NFR-SEC-003, NFR-COMP-004) — `Repository.Packing/BlobWriter`'s `AppendSealedRecordAsync` copies the sealed bytes verbatim and re-frames only the header, because the key is the object's, the nonce rides the record's prefix and the 51-byte AAD names no position ([ADR-0052](adr/0052-relocatable-records-format-v3.md)). The row above is the same question answered the other way one format later; both stand, because a table that recorded only the newer answer would let a reader carry it back to the format every shipped repository is |
| A blob holding a live minority is rewritten without a content key, and the space comes back | Compact a blob whose reachable records are a minority: the pass needs a key that could open one; or the drained blob is never condemned and the archive never shrinks; or a relocated record does not read back | `Repository.Tests/BlobCompactionTests`, `Repository.Tests/CompactionIndexTests`, `InterruptionTests/CompactionInterruptionTests`, `Hosts.Tests/CompactionRetentionTests` | **Proved** (FR-GC-011, FR-GC-004, NFR-SEC-003) — the compactor is constructed holding nothing that could decrypt and completes, and the relocated ciphertext is byte-identical to the source's. Scoped to format 3 and to local paths: a format-2 set is refused by name, and a peer's replica is never compacted |
| The engine does not depend on a listing reflecting what a store holds | Run a pass against a store whose listings lag: a snapshot the listing has not caught up to has its blobs condemned, or a destination's keep-set is built from an incomplete view and trims the only other copy | `Storage.ContractTests/LaggingObjectStoreTests`, `Retention.Tests/EventualListingTests`, `Repository.Tests/EventualListingIndexTests`, `Replication.Tests/CopierEventualListingTests` | **Partly proved** (NFR-PORT-005, NFR-COMP-005) — the falsifier is run and the answer is a refusal rather than a defence: collection reasons from absence end to end, so against anything but a strongly-consistent listing it reports its plan and condemns nothing, and a destination's keep-set is refused rather than built ([ADR-0012](adr/0012-storage-provider-contract.md) Amendment 3). The planes that reason from presence do survive and are pinned: an unseen delta is an unresolved gap, a stale head collides on its conditional put, a replication pass re-offers and is refused. **Partly**, on two counts. The refusal is not the property the row claims — an engine that collects on such a store needs an attested witness of completeness for the snapshot plane, which does not exist. And the whole row is exercised by an instrument rather than by a provider: there is one provider and it promises `Strong`, so what is proved is what the engine does when told a listing may lag, not what it does against a store that actually lags |
| A repository moves to a newer format without rewriting anything it already holds, and every copy learns of it | Upgrade a set, then look at a destination after a reconciling pass — a copy still claiming the older format, or one that will not open, falsifies it; so does an upgraded set that goes on sealing the older format, or one that stops restoring what it wrote before | `Repository.Tests/FormatUpgradeRecordTests`, `Repository.Tests/EffectiveFormatTests`, `Hosts.Tests/FormatUpgradeTests` | **Proved** (FR-MAN-019, NFR-COMP-004) — an append-only signed record under `format-upgrade/`, not a rewritten descriptor, because a destination is seeded with the descriptor if absent, a peer keeps the copy it has and `repository-format` may not be named by a retention instruction, so a rewrite would move the source alone ([ADR-0066](adr/0066-the-format-upgrade-record.md)). The record rides every copy path with no protocol change, and is refused by name when an instruction names it for deletion. Two limits are stated rather than hidden: a destination holds newer blobs before it holds the record that explains them, until the next reconciling pass — which costs nothing, because every blob declares its own container — and a build older than the newer format meets it at that first blob, refusing as damage rather than by name |

### What leaves the machine

| Invariant | What would falsify it | Proof | State |
|-----------|-----------------------|-------|-------|
| Nothing leaves the device that nobody asked for | Put a default installation through its ordinary work and watch the process's own network instrumentation: a connect to an address on an IP network, a name resolution or an HTTP request falsifies it — and so, before any run, does a shipped assembly that could make one | `ArchitectureTests/TelemetrySilenceTests`, `Hosts.Tests/DefaultBuildSilenceTests` | **Partly proved** (NFR-PRIV-001) — proved in two halves that answer different questions. The build holds no **means**: no shipped assembly references an HTTP client, outbound capability is confined to the five that are the peer protocol and the loopback IPC, nothing attaches a `MeterListener` or an `ActivityListener` to the in-box instruments — the route that needs no package at all ([ADR-0027](adr/0027-services-scheduling-status-telemetry.md) §3) — and the twelve packages the product ships are pinned as a set, because an update check, a crash reporter and a usage beacon share no name, only the fact that somebody added a dependency. And a default **run** is captured: setup, a backup to a local path, status, snapshots, a restore and a retention pass, driven through the transport an operator's terminal uses, reaching no IP address and resolving no name. The capture is held honest by a positive control — the product's one legitimate outbound connection, a peer destination the operator configured, decoded back to the endpoint the configuration named — which earned its place at once: breaking the instrument left the silence assertion **passing** and only the liveness cases red. **Partly**, on the limit the halves exist to cover for each other: the capture observes this process, not the machine, so it is not a packet capture and cannot see a child process; what makes one observed run worth generalising from is a build that cannot reach the network and a package list that cannot grow in silence |

### Destinations and durability

| Invariant | What would falsify it | Proof | State |
|-----------|-----------------------|-------|-------|
| `verified` means bytes were read at the destination and checked against evidence it does not hold | Corrupt a blob at a set's only destination, and separately let a converged set sit with nothing to copy | `Hosts.Tests/DestinationVerificationTests`, `Hosts.Tests/DirectShipVerificationTests`, `Replication.Tests/ReplicaVerifierTests` | **Proved** — a peer answers a keyed range challenge; a readable destination has its sampled blobs *opened* at the replica, so the AEAD tag the writer computed is the evidence and no second copy is needed. Challenges are due on the proof's age, not on a copy being due. A set with **no** evidence independent of the destination — a direct-ship set shipping only to a peer, where this installation holds no content at all — is proved by **reading the replica back** through the retrieval session and authenticating a record inside a sampled blob, which needs no second copy because the peer never held the key that computed the tag ([ADR-0058](adr/0058-peer-write-adapter.md) §8). `Hosts.Tests/PeerReadBackVerificationTests` rots the peer's blobs and the pass refuses to call it in sync; `Hosts.Tests/DirectShipPeerTests` holds that a peer which will not serve the read-back is said to be unchecked rather than quietly assumed good (FR-VER-001, FR-VER-002) |
| A protected historical piece stays provable after the source copy is discarded | Delete the source copy, then corrupt the destination's | `Hosts.Tests/DirectShipVerificationTests`, `Hosts.Tests/PeerReadBackVerificationTests`, `Replication.Tests/ReplicaVerifierTests`, `Repository.Tests/CatalogueTests` | **Proved** (FR-VER-001, FR-WOR-003) — a blob is proved by opening it at the replica, which needs no source copy at all, and the write-only data plane, whose records the service cannot open, is proved by the **digest tier**: the whole sealed blob hashed at the destination against the digest the writer signed into the index, which a rebuilt catalogue now keeps. One rotted byte under a sealed record with the footer left whole fails by digest, at a local path and at a peer; a blob above the per-pass byte budget is left unproved and said, never looped. Over a peer a format-2 blob is the whole blob read back through the retrieval session — the bytes crossing the wire are the proof — walking the peer's inventory on a cursor under a peer budget of its own. At format 3 the delta publishes a **Merkle root** beside the digest, and the peer is asked for **one leaf and its authentication path** instead ([ADR-0065](adr/0065-merkle-commitment-and-chunk-possession.md)): the leaf's bytes are checked against the root the writer signed, the path proves nothing by itself because the peer may cache it, and one byte rotted under a sealed record fails by chunk. A digest challenge in which the peer hashes its own copy stays refused as a self-report ([ADR-0058](adr/0058-peer-write-adapter.md) §8 as amended). The chunk proof is **sampled** — one leaf, not the blob — and is counted apart from the whole-blob tier for that reason. Since format 3 became what the product creates ([ADR-0066](adr/0066-the-format-upgrade-record.md)) this tier is reachable by an ordinary installation rather than only by a fixture and a test seam; a set still at format 2 publishes no root and is proved by the whole-blob tier, which is the one asymmetry between the formats a person would notice |
| A peer never trims below the retention floor it agreed to | Ask it to trim past the floor, from the hub that planned the trim | `Retention.Tests/PeerRetentionTests` | **Proved** (FR-GC-007, FR-GC-010) |
| Retiring a staging archive never strands live history | Retire while a destination still lacks a blob a live snapshot reaches | `Hosts.Tests/DirectShipMigrationTests` | **Proved** (FR-DEST-016) |
| A direct-ship set keeps no copy of the backup on the machine it is protecting, whatever kind its destinations are | Capture a set whose only destination is a paired peer, then look for content under the agent's roots and try to restore from the peer's replica alone | `Hosts.Tests/DirectShipPeerTests`, `Hosts.Tests/DirectShipTests` | **Proved** for both served kinds ([ADR-0058](adr/0058-peer-write-adapter.md)): the agent's state gains metadata only, the peer ends holding a replica byte-identical to that metadata plus the content, and the standalone recovery tool restores the captured file out of it with the passphrase alone. A second capture adds to the replica without disturbing the first, and an unreachable peer is dropped while a sibling carries the run (FR-DEST-013, FR-DEST-015) |
| An interrupted transfer exposes no partial object, and a re-run resumes rather than restarting | Interrupt mid-transfer — between objects, and inside one — then run again | `InterruptionTests/StoreCopyOrderTests`, `Hosts.Tests/PeerReplicationTests`, `Hosts.Tests/PeerResumeTests` | **Proved** for the peer wire, at both granularities ([ADR-0057](adr/0057-resumable-object-transfer.md)): no partial object is ever visible, a re-run resumes from the destination's inventory, and a transfer cut **inside** an object sends only the remainder — verified by the source against a digest of the bytes the destination claims, so a damaged prefix restarts the object rather than being built on. The cut itself is now exercised rather than assumed. A local-path copy still restarts the object it was cut inside, deliberately: a re-copy there reads local disk (FR-REP-003) |
| Sync work is proportional to what changed, not to the size of the repository | A repository at scale **M** with a 0.01% delta; count listings, requests and peak memory | `Replication.Tests/CopierListingCostTests`, `Application.Tests/ReconciliationGateTests`, `Hosts.Tests/IncrementalSyncTests` | **Partly proved** — the shape is held and the scale is not. What is not proved is the row's own falsifier: nothing runs at scale **M**, so the claim that the remaining per-pass work stays proportional there is reasoning rather than measurement (NFR-PERF-016, NFR-PERF-005) |
| A destination that quietly loses an object does not stay lost | Delete an object out of a replica, then let passes run | `Hosts.Tests/IncrementalSyncTests`, `Hosts.Tests/DestinationVerificationTests`, `Hosts.Tests/RecoveryDrillTests` | **Proved** for a local-path destination, by three mechanisms that do not share a failure mode (FR-REP-005, FR-VER-002, FR-DRL-002): the pass that reads both inventories through comes due on its own cadence whatever the watermark says; verification opens sampled bytes at the destination; and the drill restores a file from it. A peer is witnessed from the inventory every push already declares, before the push filters or drops anything: the granted convergence run drops nothing at the peer, a direct-ship set is healed over the retrieval session — and a staging set too, a file longer than one retrieval chunk reassembled byte for byte — and a third backup's journal is at the peer byte for byte ([Amendment 1](adr/0062-the-destination-is-the-rollback-witness.md#amendment-1--the-peer-is-a-witness-too-from-the-inventory-it-already-declares-2026-09)). ## How to use this

**When adding an invariant**, add the row before the code. The falsifier
column is the useful half: an invariant whose falsifier cannot be written down
is not yet stated precisely enough to be worth testing.

**When a row moves to Proved**, it moves because a named class goes red
without the code, not because the code looks right. A test that passes both
with and without the invariant is not a proof of it, and the checker cannot
tell the difference — that judgement is the reviewer's.

**When a row stays Unproved**, that is information, not a failure. Three of
the rows above are phase-4 work correctly not started. What the register
refuses is the fourth possibility: an invariant everyone assumes and nobody
has looked at.
