## 1. Executive summary

FallbackPlan will be an open-source backup and archival platform for Windows, macOS, and Linux. Its initial purpose is to restore a capability the consumer market has largely withdrawn: a user can back up one computer to another computer they control or trust, across a LAN or the internet, without requiring a proprietary cloud service.

FallbackPlan will combine selected strengths of:

• Consumer peer backup services: simple computer-to-computer backup, continuous protection, historical versions, flexible retention, destination independence, and a consumer-friendly operating model.
• Peer synchronisation protocols: peer identity, direct encrypted device communication, discovery, relay-assisted connectivity, efficient block transfer, and resilient distributed operation.
• Content-addressed snapshot repositories: immutable snapshots, content-defined chunking, content-addressed storage, simple repository backends, explicit consistency invariants, and repairability.
• Layered blob-store repositories: layered repository architecture, encrypted metadata, pluggable blob stores, packing, caching, policy-based snapshots, and scalable content indexing.
• Plugin-oriented backup clients: broad storage-provider support, scheduling, web-based administration, and approachable configuration for home and small-business users.

FallbackPlan must not merely reproduce these products. It should deliberately address their recurring weaknesses:

• proprietary or insufficiently documented repository formats;
• large monolithic metadata files that become performance and recovery bottlenecks;
• excessive dependence on a local database that can diverge from the remote repository;
• unsafe deletion propagation associated with file synchronisation;
• fragile repository maintenance and pruning;
• poor multi-writer coordination;
• expensive object-store enumeration and request patterns;
• difficult credential and encryption-key recovery;
• unclear recovery guarantees;
• migrations that require restoring every file before changing products;
• interfaces that expose implementation concepts rather than the user's recovery objective.

The first architectural centre of FallbackPlan will be a streaming archive engine that divides files into configured-size segments, hashes and compares them by version, encrypts changed segments independently, and packs them into configured-size immutable blobs. This engine will underpin the broader versioned, encrypted, content-addressed repository. A repository is replicated between FallbackPlan instances and storage providers; live folders are not treated as bidirectional synchronisation roots. Each source device publishes immutable snapshots. A destination may hold snapshots for multiple source devices. Deletions create new snapshot state and do not immediately delete historical content.

Legacy archive migration will be implemented as a separate, read-only compatibility subsystem. It will inspect and restore supported legacy archives, map their file/version history into a neutral import model, and write equivalent FallbackPlan snapshots. The native repository will never depend on legacy structures.

## 2. Product vision

### 2.1 Vision statement

> FallbackPlan gives every computer a safe fallback: encrypted, versioned copies held on computers and storage that the user chooses.

### 2.2 Product promise

A user should be able to answer all of the following without specialist knowledge:

1. Is this computer protected?
2. Where are its backups stored?
3. When was the last independently verified recoverable snapshot?
4. Can I restore after this computer is destroyed?
5. Can I move my archive to another provider without starting again?
6. Can I recover without a FallbackPlan-operated service?

### 2.3 Core principles

1. Recovery is the product. Backup completion is not sufficient; recoverability must be verified.
2. The user owns the repository. No FallbackPlan-operated cloud account is required.
3. Open format, open protocol, open implementation. The repository and wire specifications must be published and versioned.
4. No silent destructive synchronisation. Source deletion is recorded as history; retention and garbage collection are independent operations.
5. Encryption before transport. Storage nodes and cloud providers do not require access to plaintext content or filenames.
6. Metadata must scale incrementally. No repository-wide monolithic manifest is permitted.
7. Every durable object is independently verifiable. Corruption should be localised, detectable, and repairable.
8. Caches are disposable. A local index or database may accelerate operations, but the repository remains the source of truth and can rebuild it.
9. Interruption is normal. Every operation must tolerate process termination, loss of connectivity, and eventually consistent storage.
10. Compatibility is isolated. Importers translate legacy formats into a stable neutral model and cannot dictate the native design.

## 3. Scope

### 3.1 Initial scope

The first production-capable release will support:

• selection of local files and directories for backup;
• scheduled and change-triggered snapshot creation;
• versioned, point-in-time snapshots;
• encrypted backup to another FallbackPlan instance;
• encrypted backup to a local directory or mounted filesystem;
• repository replication between FallbackPlan instances;
• Azure Blob Storage;
• Amazon S3 and S3-compatible object stores;
• restore by device, snapshot, date, path, pattern, or selection;
• configurable retention policies;
• repository integrity verification and repair workflows;
• bandwidth, CPU, concurrency, and schedule controls;
• resumable transfers;
• a command-line interface;
• a local web administration interface;
• headless service operation;
• legacy archive assessment and migration for explicitly supported archive variants;
• export of repository metadata and recovery keys in a documented recovery kit.

### 3.2 Subsequent scope

Later releases may add:

• further S3-compatible and cloud object-store providers, SFTP, WebDAV, SMB-aware and removable-media providers;
• peer discovery through optional public infrastructure;
• relay services that cannot decrypt content;
• multi-user household and small-business administration;
• mobile restore and photo ingestion;
• filesystem snapshots through VSS, APFS, Btrfs, ZFS, and LVM integrations;
• database-aware pre/post snapshot hooks;
• repository mirroring across storage classes and geographic locations;
• immutable/WORM retention targets;
• object-lock integration;
• erasure coding for peer sets;
• public restore links using separately wrapped, scoped keys;
• importers for other backup tools' repositories where licensing and format stability permit.

### 3.3 Explicit non-goals for the initial release

• full-disk imaging or bare-metal recovery;
• operating-system deployment;
• bidirectional working-folder synchronisation;
• collaborative file editing;
• proprietary cloud hosting operated by the project;
• ransomware detection as a substitute for endpoint security;
• automatic deletion of source data after backup;
• transparent filesystem mounting as the only restore method;
• guaranteed conversion of every historical legacy variant.

### 3.4 Functional requirements

The initial solution must meet the following functional requirements. Requirements use the identifiers FR-* so they can be traced into architecture decisions, implementation work items, and tests.

**Archive engine**

• FR-ARCH-001 — Configurable segmentation: The engine shall split each regular file into deterministic, equal-length logical segments using a configured segment size. Only the final segment may be shorter.
• FR-ARCH-002 — Streaming operation: Segmentation, hashing, compression, encryption, and packing shall operate as a bounded-memory stream and shall not require the complete file or blob to be resident in memory.
• FR-ARCH-003 — Segment hashing: The engine shall calculate a cryptographic plaintext hash for each segment before encryption and use it to identify unchanged segments between file versions.
• FR-ARCH-004 — Version reuse: When a new file version is captured, unchanged segment references shall be reused rather than writing duplicate segment payloads.
• FR-ARCH-005 — Changed-segment storage: New or changed segments shall be compressed where beneficial, encrypted independently, authenticated, and appended to a configured-size immutable blob.
• FR-ARCH-006 — Cross-blob files: A file and a single file version may reference segments held in any number of blobs. Blob boundaries shall not affect file semantics or restore order.
• FR-ARCH-007 — Configurable blob size: The target and maximum blob sizes shall be configuration driven, validated against provider limits, and recorded in the repository format profile used for each write generation.
• FR-ARCH-008 — Configurable encryption: The encryption algorithm, key generation, and algorithm parameters shall be selected from supported configuration profiles and recorded per encrypted record. Unsupported or unsafe combinations shall be rejected.
• FR-ARCH-009 — Independent authentication: Every encrypted segment record shall be independently authenticated so corruption can be localised without trusting the remainder of its blob.
• FR-ARCH-010 — Deterministic reconstruction: File versions shall be reconstructed from ordered segment references containing logical offset, logical length, plaintext hash, blob identifier, record offset, stored length, compression profile, and encryption profile.
• FR-ARCH-011 — Resumable blob construction: Interrupted blob creation shall either resume from a verified local spool checkpoint or be safely abandoned without becoming visible as a committed repository object.
• FR-ARCH-012 — Blob sealing: A blob shall become immutable after sealing. Its authenticated footer shall contain sufficient record metadata to inspect and rebuild repository indexes.
• FR-ARCH-013 — Empty, sparse, and large files: The engine shall correctly represent empty files, sparse extents, files smaller than one segment, and files spanning many blobs.
• FR-ARCH-014 — Optional future chunking profiles: The format shall permit future content-defined or variable-size segmentation profiles without changing the semantics of existing fixed-size segment records. The first implementation shall use fixed equal-length segmentation.

**Manifest and lookup**

• FR-MAN-001 — Repository source of truth: Authoritative manifests and indexes shall be stored as immutable repository objects. No local database shall be required to interpret or restore a committed snapshot.
• FR-MAN-002 — Rebuildable local catalogue: Each instance shall maintain a local transactional catalogue for fast path, file-version, segment-hash, blob-location, and snapshot lookups. The catalogue shall be disposable and fully rebuildable from repository objects.
• FR-MAN-003 — File-version manifest: Each file version shall have an immutable manifest containing canonical path identity, metadata, logical length, ordered segment references, parent-version reference where applicable, and a whole-file verification hash.
• FR-MAN-004 — Hierarchical manifests: Directory trees and snapshots shall reference file-version manifests through immutable, sharded tree objects; no snapshot shall require one monolithic repository-wide manifest.
• FR-MAN-005 — Fast path lookup: The local catalogue shall support lookup of a path within a selected snapshot without scanning unrelated snapshots, trees, blobs, or segment records.
• FR-MAN-006 — Fast deduplication lookup: The local catalogue shall support lookup of a segment plaintext hash and segmentation/encryption domain to determine whether a reusable segment already exists.
• FR-MAN-007 — Pack-local recovery index: Every sealed blob shall include an authenticated footer or sidecar recovery index listing each contained record, its keyed object identifier, physical offset, stored length, logical length, and encoding profiles.
• FR-MAN-008 — Incremental global indexes: Writers shall publish immutable index deltas after blobs are durable. Periodic checkpoint indexes shall compact deltas by shard without invalidating prior generations.
• FR-MAN-009 — Rebuild modes: The engine shall support quick rebuild from the latest trusted checkpoint plus deltas, and full forensic rebuild by scanning all sealed blob recovery indexes and snapshot roots.
• FR-MAN-010 — Partial availability: Listing and restore shall become available incrementally during a catalogue rebuild as soon as the required snapshot, tree, file, and blob mappings are known.
• FR-MAN-011 — Rebuild verification: Rebuild shall verify signatures, authenticated metadata, record bounds, duplicate/conflicting mappings, generation ordering, and references to missing blobs.
• FR-MAN-012 — Damage reporting: The engine shall distinguish catalogue corruption, missing index objects, missing blobs, corrupt records, and unreachable orphan data, and report which snapshots and file versions are affected.

**Snapshot, restore, and replication**

• FR-SNP-001: The engine shall publish immutable point-in-time snapshots only after all required blobs and index deltas are durable.
• FR-SNP-002: File deletion shall create new snapshot state and shall not directly delete older file versions or segment records.
• FR-RST-001: Restore shall support selecting device, backup set, snapshot or time, path, file version, and destination.
• FR-RST-002: Restore shall verify each segment after decryption and the complete reconstructed file before reporting success.
• FR-REP-001: Repositories shall replicate between FallbackPlan instances by exchanging immutable blobs, manifests, snapshots, and index generations.
• FR-REP-002: Azure Blob Storage and Amazon S3/S3-compatible stores shall be supported through the common object-store abstraction.
• FR-REP-003: Transfer shall resume at verified blob or range boundaries and shall never expose a partially written blob as committed.

**Legacy archive import**

• FR-CP-001: legacy archives shall be opened read-only.
• FR-CP-002: The importer shall map recoverable legacy file versions into the same native segment, blob, manifest, and snapshot pipeline used by filesystem capture.
• FR-CP-003: Conversion shall stream data directly from the legacy archive into native blobs without requiring a complete temporary plaintext restore.
• FR-CP-004: Import shall be resumable, produce provenance records, and verify imported file versions against all source hashes or checksums available from the legacy archive.
• FR-CP-005: Unsupported archive versions, encryption schemes, or damaged records shall be identified before destructive or high-volume processing and shall never modify the source archive.

### 3.5 Non-functional requirements

The solution must meet the following quality and operational requirements.

**Performance and scalability**

• NFR-PERF-001: Memory use shall be bounded by configured pipeline concurrency, segment size, and blob-buffer limits, not by file size, file count, version count, or repository size.
• NFR-PERF-002: The archive pipeline shall support parallel read, hash, compression, encryption, and blob-write stages while preserving deterministic file segment order.
• NFR-PERF-003: Unchanged files and unchanged segments shall avoid payload reads and writes when trustworthy metadata and segment hashes permit reuse.
• NFR-PERF-004: Local path and segment lookups should be logarithmic or constant-time through indexed catalogue access and must not require remote object enumeration per lookup.
• NFR-PERF-005: Repository metadata growth shall be incremental; committing one snapshot shall not rewrite metadata proportional to total repository size.
• NFR-PERF-006: Cloud operation shall minimise transaction amplification by packing many independently encrypted segments into configured-size blobs.
• NFR-PERF-007: The implementation shall be benchmarked with millions of files, high version counts, multi-terabyte files, and repositories containing at least tens of millions of segment references.

**Reliability and recoverability**

• NFR-REL-001: Process termination, machine restart, network loss, out-of-space conditions, and provider timeouts at any pipeline step shall not make a previously committed snapshot unreadable.
• NFR-REL-002: The local catalogue shall be treated as a cache. Deleting or corrupting it shall not cause repository data loss.
• NFR-REL-003: A full catalogue rebuild shall be possible from repository format metadata, sealed blob recovery indexes, index generations, and snapshot roots.
• NFR-REL-004: Corruption shall be localised to the smallest practical unit—segment record, blob, manifest, or snapshot—and unaffected snapshots shall remain available.
• NFR-REL-005: All maintenance operations shall be resumable, cancellable, idempotent where practical, and safe to repeat.
• NFR-REL-006: The repository shall retain enough redundant structural metadata to recover when global index objects are lost, while avoiding duplication of user payload data solely for metadata recovery.

**Security and privacy**

• NFR-SEC-001: File content, filenames, paths, file metadata, manifests, and segment hashes shall be encrypted or keyed before leaving the trusted client boundary.
• NFR-SEC-002: Only reviewed AEAD algorithms and approved configuration profiles shall be accepted. Insecure algorithm selection shall not be available as a compatibility switch.
• NFR-SEC-003: Nonce uniqueness and key separation shall be guaranteed by construction and tested across concurrent writers and resumed operations.
• NFR-SEC-004: A compromised store or relay shall not be able to decrypt content, enumerate plaintext paths, or confirm possession of a known plaintext through raw unkeyed object identifiers.
• NFR-SEC-005: Repository metadata and writer publications shall be authenticated so rollback, substitution, truncation, and writer-identity conflicts can be detected.
• NFR-SEC-006: Secrets shall not be written to logs, telemetry, crash dumps, manifests, or ordinary configuration exports.

**Compatibility and evolvability**

• NFR-COMP-001: Repository, blob, record, manifest, index, and encryption profiles shall be independently versioned and explicitly discoverable.
• NFR-COMP-002: Existing repositories shall remain readable when new segment, compression, or encryption profiles are introduced.
• NFR-COMP-003: Unknown required features shall cause safe refusal; unknown optional fields shall follow documented preservation or ignore rules.
• NFR-COMP-004: The repository format and conformance fixtures shall be publicly documented sufficiently for an independent restore implementation.
• NFR-COMP-005: Provider-specific capabilities shall not leak into snapshot or file-version semantics.

**Operability and usability**

• NFR-OPS-001: The engine shall expose measurable pipeline throughput, queue depth, deduplication ratio, compression ratio, blob utilisation, catalogue state, verification state, and destination durability.
• NFR-OPS-002: User-facing status shall distinguish captured, packed, replicated, verified, policy-compliant, degraded, and unrecoverable states.
• NFR-OPS-003: Configuration shall be schema-versioned, validated before use, and exportable without secrets. Effective values used for each snapshot shall be preserved.
• NFR-OPS-004: Default settings shall be safe for consumer hardware while allowing advanced overrides for segment size, blob size, concurrency, compression, encryption profile, and provider behaviour.
• NFR-OPS-005: Recovery shall be possible from a clean machine using only the repository, supported recovery software, and the recovery kit.

**Portability and maintainability**

• NFR-PORT-001: Core repository processing shall run on supported Windows, macOS, and Linux versions without requiring a platform-specific database engine.
• NFR-PORT-002: Storage, cryptography, compression, segmentation, catalogue, and legacy-import concerns shall be separated behind tested interfaces.
• NFR-PORT-003: The codebase shall support deterministic fixtures and property-based tests for all repository encodings and state transitions.
• NFR-PORT-004: Public APIs shall use asynchronous streaming, cancellation, bounded concurrency, and explicit result/error types.

## 4. Lessons adopted from existing products

### 4.1 Consumer peer-to-peer backup services

The legacy archive model splits files into blocks, deduplicates, compresses, encrypts, and stores them with metadata describing file paths and versions. Its original consumer appeal came from supporting computer and folder destinations rather than requiring a cloud service.

**Adopt**

• continuous or frequent incremental protection;
• multiple independent destinations per backup set;
• computer-to-computer backup;
• long historical version retention;
• restoration to a replacement computer;
• simple consumer language around protection and recovery;
• source-side encryption;
• block reuse across versions.

**Improve**

• publish the repository format and migration guarantees;
• avoid repository-wide monolithic manifests;
• shard and content-address metadata;
• provide independent integrity-check and recovery tooling;
• make encryption-key export a first-class workflow;
• keep the repository usable without authentication to a vendor service;
• make maintenance online, incremental, bounded, and cancellable;
• ensure older readers fail safely when encountering newer format features;
• support archive migration without restoring the full archive to temporary plaintext storage.

That class of product documents that large file and history manifests can interfere with scanning, synchronisation, backup, restore, and maintenance. FallbackPlan must treat this as a primary design constraint, not a late optimisation.

### 4.2 Peer synchronisation protocols

Peer synchronisers demonstrate strong peer-to-peer identity and transport architecture. Its Block Exchange Protocol exchanges file metadata and missing blocks between authenticated devices, while discovery and relay protocols solve connectivity problems.

**Adopt**

• cryptographic device identities;
• explicit device approval and trust;
• direct peer connectivity where possible;
• LAN discovery;
• optional global discovery;
• relay fallback without relay access to plaintext;
• protocol negotiation and capability advertisement;
• block-level transfer requests;
• resumable, parallel, bounded transfers;
• independent control and data channels;
• transparent connection-path reporting.

**Do not copy directly**

FallbackPlan is a backup system, not a global working-tree reconciler. It must not choose a single current global file state and propagate deletion or conflict resolution as its primary model. A source device publishes snapshots; destinations preserve them according to retention policy.

### 4.3 Content-addressed snapshot repositories

This family demonstrates a compact repository architecture based on snapshots, tree objects, data blobs, pack files, indexes, locks, and content-defined chunking. Its documented write ordering provides an important durability rule: durable data first, indexes second, snapshot references last.

**Adopt**

• immutable snapshots;
• Merkle-style directory trees;
• content-defined chunking so inserted bytes do not invalidate all later chunks;
• pack files for efficient storage operations;
• repository invariants and documented write ordering;
• repository checks that can rebuild indexes from packs;
• explicit shared and exclusive maintenance locks;
• append-before-reference semantics;
• local cache as an optimisation only;
• pruning as a separate maintenance concern.

**Improve**

• design multi-device writers from the beginning rather than treating concurrent maintenance as an exceptional condition;
• reduce dependence on listing large object namespaces;
• support repository event journals and compacted index generations;
• expose recoverability and damaged-snapshot scope in user-facing terms;
• support background healing from replicas;
• avoid requiring a single global exclusive operation for routine retention where generation-based collection can be used.

### 4.4 Layered repositories over a minimal blob store

This family's repository layers simple blob storage beneath content-addressed blocks, encrypted metadata, indexes, caching, packing, and snapshot policies.

**Adopt**

• a minimal blob-store abstraction;
• content-addressed encrypted blocks;
• packs sized for high-latency and request-priced object stores;
• index recovery data embedded in packs;
• encrypted filenames and metadata;
• policy inheritance;
• repository-server mode for shared repositories;
• caching designed for remote latency;
• independently configurable chunking, compression, packing, and encryption suites through repository format versions.

**Improve**

• minimise repository-wide format configuration that cannot evolve per generation;
• make key hierarchy and recovery-kit behaviour straightforward for consumers;
• distinguish clearly between repository password rotation and data-key rotation;
• establish deterministic compatibility and conformance fixtures for third-party readers.

### 4.5 Plugin-oriented clients with an authoritative local database

This family demonstrates the value of a web interface, broad backend support, schedules, filters, and accessible configuration.

**Adopt**

• browser-based local management;
• broad provider plugin model;
• job scheduling and notification;
• include/exclude rules;
• approachable restore workflows;
• provider-specific advanced settings behind a common interface.

**Improve**

• do not make a single local SQLite database authoritative;
• allow complete reconstruction from repository objects;
• reduce volume-chain fragility;
• isolate provider plugins from repository semantics;
• build deterministic state-machine and interruption testing into the initial implementation;
• avoid exposing an unbounded list of backend-specific options in the primary user experience.

## 5. Core domain model

### 5.1 Terms

|Term|Meaning|
|----|-------|
|**Device**|A cryptographically identified FallbackPlan installation.|
|**Source**|A device and selected filesystem roots whose state is captured.|
|**Backup set**|Source selection, exclusions, schedule, retention, and destinations.|
|**Snapshot**|Immutable point-in-time representation of a backup set.|
|**Repository**|Logical collection of encrypted content, metadata, indexes, and snapshots.|
|**Store**|Physical blob/object storage holding repository objects.|
|**Replica**|A store or peer containing a copy of all or a selected subset of repository objects.|
|**Blob**|Immutable physical container holding independently encrypted segment or metadata records; equivalent to a pack in some backup systems.|
|**Segment**|Deterministic logical portion of a file, fixed-size except for the final segment in the initial format profile.|
|**Tree**|Immutable directory object referencing files, child trees, and metadata.|
|**Manifest**|Small immutable snapshot descriptor referencing a root tree and policy context.|
|**Generation**|Published repository index/checkpoint state.|
|**Lease**|Time-limited coordination record for a writer or maintenance operation.|
|**Recovery kit**|Export containing repository identity, key material or wrapped keys, format details, and recovery instructions.|

### 5.2 Snapshot semantics

A snapshot records:

• source device identity;
• backup-set identity;
• capture start and completion time;
• parent snapshot(s), where applicable;
• root tree identifier;
• filesystem capabilities and case-sensitivity;
• policy version;
• consistency method used, such as live scan or VSS;
• errors, unreadable paths, and partial-capture status;
• source clock observations;
• client and repository format versions;
• a signed snapshot declaration.

Snapshots are never modified. Corrections create new declarations or tombstone/administrative records without rewriting historical objects.

### 5.3 Archive replication versus folder synchronisation

The first release will replicate repository objects, not live source folders.

This means:

• a source scan produces a snapshot;
• the snapshot references immutable trees, file-version manifests, and segments;
• peers exchange missing immutable repository objects;
• publication of the snapshot occurs only after all referenced objects are durable at the required destination level;
• a file deletion appears in a later snapshot but does not erase earlier versions;
• retention calculates which snapshots remain protected;
• garbage collection removes unreachable objects only after safety checks and grace periods.

This model provides the transfer efficiency associated with synchronisation while preserving backup semantics.

## 7. Native repository format

### 7.1 Format goals

The repository format must be:

• documented;
• append-oriented;
• content-addressed;
• encrypted by default and without an unencrypted mode;
• resilient to partial writes;
• efficient on local disks and object storage;
• capable of concurrent readers and multiple snapshot writers;
• reconstructable without a local database;
• self-describing by version;
• independently implementable;
• testable using public conformance vectors;
• migratable without rewriting all content for every minor format change.

### 7.2 Logical object classes

```text
/repository-format
/keys/<key-id>
/blobs/data/<shard>/<blob-id>
/blobs/meta/<shard>/<blob-id>
/index/delta/<generation>/<index-id>
/index/checkpoint/<generation>/<checkpoint-id>
/snapshots/<device-id>/<backup-set-id>/<snapshot-id>
/journal/<writer-id>/<sequence>
/leases/<scope>/<lease-id>
/tombstones/<object-type>/<object-id>
/audit/<period>/<record-id>
```

The exact physical naming convention must avoid leaking source names, user names, paths, timestamps, and content hashes where that would aid traffic or confirmation attacks. Identifiers exposed to the store should be keyed or encrypted identifiers rather than raw plaintext hashes.

### 7.3 Content addressing

Use two identifiers:

• Plain content identifier: calculated from canonical plaintext for in-client deduplication and integrity verification; never exposed directly to an untrusted store.
• Repository object identifier: derived using a repository-specific keyed function from the content identifier and object type.

This prevents a storage provider from testing whether a repository contains a known public file by hashing that file and looking for its raw digest.

### 7.4 File segmentation and version differencing

The first implementation shall use fixed-size, equal-length logical segments. The configured segment size applies to the file stream; only the final segment may be shorter. Segment boundaries are independent of blob boundaries.

For each file version, the engine shall:

1. read the file as a bounded stream;
2. divide it into configured-size logical segments;
3. calculate the plaintext cryptographic hash of each segment;
4. compare each segment hash with the corresponding segment position in the prior file version and, where useful, the repository-wide segment catalogue;
5. reuse the existing segment reference when the hash, logical length, and segmentation domain match;
6. compress a new or changed segment where beneficial;
7. encrypt and authenticate that segment independently;
8. append the encrypted record to the current blob; and
9. record the ordered segment reference in the immutable file-version manifest.

This produces segment-level version differencing: a changed file version writes only new or changed segments, while its manifest references existing encrypted segment records for unchanged positions. A file may span multiple blobs, and a blob may contain segments from many files and versions.

Initial configuration envelope to benchmark:

• default segment size: 1 MiB;
• supported segment-size range: 64 KiB to 64 MiB;
• segment size must be a validated profile value rather than an arbitrary per-file value;
• sparse extents should be represented as logical zero extents rather than materialised payload segments;
• the pipeline must not load a complete large file into memory;
• segment hashing should be pipelined with reading and use hardware acceleration where available.

Fixed segmentation makes positional comparison, random restore, deterministic testing, and legacy archive migration straightforward. It is less tolerant than content-defined chunking when bytes are inserted near the beginning of a file, because subsequent fixed segment boundaries shift. The format shall therefore identify the segmentation profile per file version and leave room for a later content-defined profile without changing existing records or manifests.

### 7.5 Compression

• compression occurs before encryption;
• use a modern, bounded-memory codec such as Zstandard;
• detect incompressible formats and avoid wasted CPU;
• record codec and version per packed object;
• set conservative defaults suitable for continuous background operation;
• allow policy overrides, but not arbitrary unsupported codecs in the core repository.

### 7.6 Encryption and key hierarchy

Recommended hierarchy:

```text
User recovery secret / hardware-protected secret
        |
        +--> Key Encryption Key (KEK)
                  |
                  +--> Repository Master Key
                            |
                            +--> Content-ID key
                            +--> Data-encryption key generation(s)
                            +--> Metadata-encryption key generation(s)
                            +--> Signing key(s)
                            +--> Peer authorisation key(s)
```

Requirements:

• use audited platform or established cryptographic libraries;
• use an AEAD scheme such as AES-256-GCM or XChaCha20-Poly1305;
• ensure nonce uniqueness by construction rather than probability alone;
• include repository ID, object type, format version, and object ID as authenticated data;
• support key generations and cryptographic agility;
• rotate wrapping keys without rewriting repository data;
• support optional full data-key rotation through background rewrite;
• use a memory-hard password KDF such as Argon2id;
• permit OS key-store protection for unattended agents;
• never log secrets, raw keys, or recovery material;
• require explicit acknowledgement before displaying or exporting recovery secrets;
• create printable and machine-readable recovery kits.

### 7.7 Config-driven blob packing

Blobs reduce request cost and improve throughput while retaining independently encrypted and authenticated segment records. In repository terminology, a blob is the immutable physical container previously described as a pack.

Blob sizing shall be configuration driven through a versioned write profile containing at least:

• target blob size;
• hard maximum blob size;
• minimum fill threshold before normal sealing;
• maximum open-blob age;
• maximum segment-record count;
• provider multipart or block-upload thresholds;
• separate data and metadata blob profiles where required.

A segment record may not be split across blobs in the first format version. When the current blob cannot hold the next complete record within its maximum size, the engine seals the blob and writes the record to a new blob. Consequently, files can span any number of blobs.

Each immutable blob shall contain:

• a versioned cleartext envelope containing only non-sensitive format and key-generation selectors;
• encrypted segment or metadata records;
• independently authenticated record headers containing keyed identifiers and physical sizing information;
• an authenticated recovery footer listing all records and their byte ranges;
• a blob-level digest covering the complete sealed representation;
• optional redundant footer copies or a small authenticated sidecar for providers where tail recovery is expensive; and
• no correctness dependency on the external global index for basic inspection and reconstruction.

Initial defaults to benchmark:

• local/peer target: 64 MiB;
• object-store target: 128 MiB;
• configurable supported range: 8 MiB to provider-safe limits;
• metadata blobs: smaller, independently configurable targets;
• no special dedicated-object rule for a large file segment unless the selected segment profile itself exceeds the normal target blob size.

Blob creation shall use a local spool or equivalent durable staging area. The blob becomes visible only after it is sealed, validated, uploaded under its final immutable identifier, and acknowledged by the destination. On providers without atomic rename, publication relies on unique final object creation followed by a later index-delta and snapshot publication.

### 7.8 Manifest architecture

Manifest storage shall separate durable truth from fast local lookup.

#### 7.8.1 Durable immutable manifests

The repository shall contain immutable, canonical, encrypted metadata objects:

• segment reference: plaintext hash or keyed content identity, logical file offset, logical length, blob ID, physical record offset, stored length, compression profile, encryption profile, and key generation;
• file-version manifest: file identity, logical length, ordered segment references and sparse extents, whole-file verification hash, timestamps, permissions, attributes, alternate stream/resource-fork references, hard-link identity, parent file-version ID, and capture diagnostics;
• tree manifest: sorted directory entries referencing child trees and file-version manifests;
• snapshot manifest: source, backup set, capture details, root-tree ID, parent snapshot, policy version, errors, and publication generation;
• policy manifest: exact effective configuration used for capture, including segment, compression, encryption, and blob profiles;
• error manifest: paths or metadata that could not be captured.

Manifests shall be sharded naturally through the tree and file-version graph. There shall be no single manifest whose size grows with the entire repository or complete snapshot history. Small metadata objects may be packed into metadata blobs, but they remain independently addressed and authenticated.

The repository encoding shall be deterministic, canonical, versioned, and independently implementable. Canonical CBOR is the leading candidate, subject to benchmarks and conformance review. Wire protocols may use Protocol Buffers independently.

#### 7.8.2 Local catalogue for fast lookup

Each agent shall maintain a local transactional catalogue, initially using SQLite with explicit abstraction so another embedded engine can be adopted later. It is a materialised index, never the repository source of truth.

The catalogue should contain indexed tables or equivalent structures for:

• repository generations and applied index deltas;
• snapshots by source, backup set, time, tag, and status;
• canonical path nodes and path-to-entry resolution per snapshot/tree generation;
• file identities and file versions;
• ordered file-version segment references;
• segment plaintext hashes/keyed identities to blob locations;
• blobs, stores, durability state, verification state, and recovery-footer state;
• parent/child manifest relationships and reachability hints;
• damaged, missing, quarantined, and orphaned objects; and
• rebuild checkpoints and provenance.

High-frequency indexes should include:

• (snapshot_id, parent_tree_id, normalised_name) for path traversal;
• (file_identity, capture_time) for version history;
• (segment_hash, logical_length, segmentation_profile) for deduplication;
• (object_id) and (blob_id, record_offset) for physical resolution;
• (store_id, blob_id) for replica and verification status; and
• (generation, shard) for incremental application.

The catalogue shall use transactional generation application. A checkpoint or index delta is either fully applied and its watermark advanced, or not visible. Normal backup and restore may continue against the last committed catalogue generation while newer generations are applied.

#### 7.8.3 Rebuild strategy

Two rebuild paths are required:

1. Normal rebuild: load the latest authenticated index checkpoint, apply subsequent immutable index deltas, then validate referenced snapshot and blob objects. This is the default fast path.
2. Forensic rebuild: enumerate sealed blobs, read and authenticate their recovery footers, reconstruct object-to-blob mappings, enumerate snapshot roots and metadata manifests, and rebuild all local lookup tables without relying on global indexes.

To make forensic rebuild practical:

• each blob recovery footer must be self-contained for physical record discovery;
• snapshot manifests must be separately discoverable from bounded prefixes;
• every index delta must identify its writer, sequence, generation, shard, predecessor/checkpoint basis, and covered blobs;
• periodic checkpoint manifests must list the complete shard set and hashes;
• recovery scanning must be parallel, bounded, resumable, and checkpointed locally;
• restore should be enabled for a selected snapshot before the complete repository catalogue is rebuilt when its dependency graph is available; and
• conflicts or duplicate mappings must be retained as forensic findings rather than silently resolved.

The rebuild process must never rewrite or repair repository objects automatically. It first produces a verified catalogue and damage report. Explicit repair or replica-healing actions occur separately.

### 7.9 Global index design

Avoid a single growing repository index. Use:

• immutable writer index deltas published only after referenced blobs are durable;
• sharding by keyed object-ID prefix and object class;
• periodic authenticated checkpoint generations that compact prior deltas;
• Bloom or XOR filters as optional lookup accelerators, never authoritative evidence of absence;
• sequence and generation watermarks for deterministic replay;
• blob-local recovery footers as the final physical recovery source;
• bounded, resumable compaction;
• retention of prior checkpoints for a configurable safety window; and
• no correctness dependency on object-listing freshness or eventual-consistency timing.

The normal read path is: local catalogue, then checkpoint/delta index, then blob recovery footer. This ordering provides fast lookup while preserving a slower independent recovery path.

### 7.10 Publication transaction

A snapshot becomes visible in this order:

1. Scan source and construct file/tree objects.
2. Segment, hash, compare, compress, encrypt, and assemble data and metadata blobs.
3. Seal and write blobs to required stores.
4. Verify store acknowledgements and optionally sample-read uploaded ranges.
5. Publish index delta(s) referencing durable blobs.
6. Publish the signed snapshot object referencing an existing root tree.
7. Publish an audit/journal record.
8. Mark the local job complete.

Readers perform the inverse: enumerate a stable snapshot set first, then load the index generation needed to resolve it.

A snapshot must never reference an object that was not already durable at its declared destination level.

## 8. Multi-writer and replication model

### 8.1 Repository ownership modes

Support two modes:

**Direct-store mode**

Multiple trusted clients hold repository credentials and write immutable objects directly. Appropriate for personal repositories and object stores.

**Repository-server mode**

Clients authenticate to a FallbackPlan Repository Server that authorises source devices, quotas, policies, and operations. Clients still encrypt content before upload. The server does not need plaintext access.

### 8.2 Writer identity

Each writer has:

• device certificate and key pair;
• repository authorisation grant;
• writer ID;
• monotonically increasing journal sequence;
• signed published records.

Conflicting sequence use, identity cloning, or rollback should raise a security alert.

### 8.3 Peer replication

Peers exchange:

1. repository identity and compatible format capabilities;
2. authorised snapshot scopes;
3. generation summaries and compact object-set filters;
4. missing snapshot declarations;
5. missing indexes;
6. missing blobs or blob ranges;
7. verification receipts.

Transfers must support:

• direct QUIC or TLS transport;
• authenticated peer identity;
• relay fallback;
• restart from verified ranges;
• dynamic concurrency;
• bandwidth schedules;
• source selection across multiple replicas;
• end-to-end content verification;
• optional local-network preference;
• fairness between backup sets.

### 8.4 Destination durability policy

A backup set may declare, for example:

```text
Snapshot complete when:
- local repository: durable, and
- at least one trusted peer: durable

Snapshot healthy when:
- local repository: verified within 7 days, and
- trusted peer: verified within 30 days, and
- cloud replica: current within 24 hours
```

The UI must distinguish:

• captured locally;
• copied to destination;
• independently verified;
• policy-compliant;
• degraded but recoverable;
• unrecoverable or incomplete.

## 11. Retention and garbage collection

### 11.1 Retention policy

Support a composable policy such as:

• keep every snapshot for 24 hours;
• keep hourly snapshots for 7 days;
• keep daily snapshots for 30 days;
• keep weekly snapshots for 12 months;
• keep monthly snapshots indefinitely;
• keep tagged snapshots indefinitely;
• keep deleted-file history for a separate duration;
• preserve at least N snapshots regardless of age.

Retention selects snapshots to protect. It does not immediately delete data.

### 11.2 Safe garbage collection

Use generation-based mark-and-sweep:

1. Establish a repository generation cut-off.
2. Enumerate all snapshots protected as of that generation.
3. Mark reachable metadata and data objects.
4. Account for active writer leases and grace periods.
5. Produce a deletion/blob-compaction plan.
6. Write replacement blobs before updating indexes.
7. Publish a new index checkpoint.
8. Tombstone old blobs.
9. Delay physical deletion for a configurable safety window.
10. Verify no current or protected snapshot references tombstoned content.
11. Delete eligible objects in bounded batches.

A dry-run report is mandatory. Interrupted collection must leave all published snapshots recoverable.

### 11.3 Ransomware and destructive-change safeguards

• flag unusual deletion or rewrite rates;
• do not automatically expire previous snapshots based solely on source change volume;
• allow destination-side retention floors that source devices cannot reduce;
• support repository-server policy locks;
• support provider object lock in later phases;
• require stronger authorisation for retention reduction and bulk snapshot deletion;
• generate signed audit records for destructive actions.

## 13. Legacy archive conversion

### 13.1 Objective

Allow users who possess a local legacy archive and the required decryption material to migrate file history into FallbackPlan without first restoring every version into a plaintext directory tree.

Such archives are described by their vendors as proprietary, with files split into blocks, deduplicated, compressed, encrypted, and tracked through manifests. Public community reader projects demonstrate that some consumer and small-business archives can be read and restored, but coverage varies by archive version and destination type.

### 13.2 Compatibility boundaries

The importer must begin with an explicit compatibility matrix:

|Dimension|Examples|
|---------|--------|
|Product line|Consumer, small-business, and enterprise endpoint variants|
|Client/archive version|Known tested versions and format variants|
|Destination|Local folder, external disk, computer, friend destination, cloud export|
|Key source|ADB, `cp.properties`, user-held custom key, passphrase-derived key|
|Filesystem|Windows, macOS, Linux|
|Metadata|permissions, ACLs, alternate streams, resource forks, hard links, sparse files|
|History|latest only, historical versions, deleted files|
|Archive health|complete, missing manifests, missing blocks, damaged blobs|

Unsupported variants must be detected and reported before migration begins.

### 13.3 Legal and licensing approach

Before implementation:

• obtain legal review of interoperability-focused reverse engineering in target jurisdictions;
• do not use another vendor's trademarks in a way that implies affiliation;
• document that users must have lawful access to their archives and keys;
• review the licence of any existing reader implementation and every dependency before reusing code;
• prefer clean-room documentation and independently written parsers where licence compatibility or provenance is uncertain;
• retain test fixtures only where redistribution is permitted;
• do not bypass authentication to the vendor's remote services or access data not supplied by the user.

The importer should be a separately packaged optional component so its dependencies and licensing remain isolated from the core.

### 13.4 Import architecture

```text
Legacy archive + key material
              |
              v
+-------------------------------+
| Legacy Archive Inspector      |
| variant detection / health    |
+---------------+---------------+
                |
                v
+-------------------------------+
| Read-only Legacy Reader       |
| manifests / history / blocks  |
+---------------+---------------+
                |
                v
+-------------------------------+
| Neutral Legacy Archive Model  |
| paths / versions / extents    |
+---------------+---------------+
                |
                v
+-------------------------------+
| FallbackPlan Import Pipeline  |
| chunk / encrypt / pack        |
+---------------+---------------+
                |
                v
       Native repository snapshots
```

**Required interfaces**

```csharp
public interface ILegacyArchiveReader
{
    ValueTask<LegacyArchiveAssessment> AssessAsync(LegacyArchiveSource source, CancellationToken cancellationToken);
    IAsyncEnumerable<LegacyVersionRecord> EnumerateVersionsAsync(LegacyImportQuery query, CancellationToken cancellationToken);
    ValueTask<Stream> OpenContentAsync(LegacyContentReference reference, CancellationToken cancellationToken);
}
```

The neutral model must represent:

• original path and platform path semantics;
• file type;
• version timestamp and ordering;
• deleted state;
• logical size;
• block/extents reference;
• available metadata;
• missing or damaged content;
• source archive identity;
• provenance and importer version.

### 13.5 Import modes

**Latest-state migration**

Imports only the newest recoverable version of each path. Fastest and least costly.

**Historical migration**

Creates FallbackPlan snapshots that preserve historical states at selected points. Because the legacy format stores versions per file rather than necessarily materialised whole-tree snapshots, the importer must reconstruct consistent logical states at chosen timestamps.

**Full-fidelity version migration**

Preserves each distinct file-version event and deleted-file history. This may create a large number of internal events; the import pipeline should coalesce events into configurable snapshot intervals while retaining per-file version timestamps as provenance metadata.

**Archive-preservation mode**

Stores the original legacy archive as opaque protected data in addition to converted snapshots. This provides evidentiary rollback if the importer later improves.

### 13.6 Migration process

1. Require the user to make a read-only copy or snapshot of the legacy archive and key database.
2. Detect archive variant and generate an assessment report.
3. Recover or accept decryption material without persisting plaintext keys unless explicitly requested.
4. Enumerate manifests and history records.
5. Validate block availability and sample decrypt/decompress operations.
6. Estimate logical data, unique readable data, versions, files, and target storage.
7. Select import mode and timestamp coalescing.
8. Stream legacy file versions into the native segmentation and blob pipeline.
9. Deduplicate naturally against already imported content.
10. Publish FallbackPlan snapshots incrementally.
11. Persist resumable import checkpoints outside the source archive.
12. Verify imported snapshots independently from the legacy reader.
13. Produce a signed migration report listing successes, omissions, damaged versions, unsupported metadata, and mappings.
14. Keep source archive untouched.

### 13.7 Import correctness requirements

• importer opens source files read-only;
• no repair or mutation of the legacy archive by default;
• every imported file version records source provenance;
• content hash is calculated after legacy-format decryption/decompression and before FallbackPlan encryption;
• comparison mode can restore both source and destination streams and compare hashes;
• malformed records are isolated rather than aborting all import where safe;
• missing blocks produce explicit incomplete-version records;
• path traversal and malicious metadata are contained;
• fuzz testing covers all binary parsers;
• import can resume without republishing completed snapshots;
• importer never silently substitutes a newer or older version.

### 13.8 Early research spike

Before committing the migration feature to a release, complete a dedicated spike:

• collect user-owned sample archives for each intended variant;
• document archive directory layout and file signatures;
• map the file and history manifests, block manifests, block files, compression, encryption, and key sources;
• reproduce an existing reader's supported operations independently;
• determine licence-compatible reuse opportunities;
• create sanitised or synthetic conformance fixtures;
• prove latest-version and historical-version extraction;
• quantify import performance and file-descriptor requirements;
• identify metadata that cannot be recovered;
• publish the compatibility matrix.

The release plan must treat legacy conversion as experimental until validated against diverse real archives.

## 14. Security model

### 14.1 Threats in scope

• untrusted cloud or peer storage reading repository content;
• tampering, truncation, replay, and object substitution;
• stolen repository media;
• compromised destination node without source keys;
• malicious or buggy peer protocol input;
• rollback to an older repository view;
• deletion by compromised credentials;
• supply-chain compromise;
• parser attacks through legacy archives;
• local privilege boundaries between UI users and service;
• secrets leaked through logs or diagnostics.

### 14.2 Threats not fully solvable by backup software

• compromised source reading plaintext before encryption;
• ransomware with access to source credentials and unlocked recovery keys;
• user loss of all recovery material;
• malicious administrators with access to all devices and retention controls;
• hardware faults across every replica without verification;
• restoration of malware already present in historical snapshots.

### 14.3 Controls

• mutual device authentication;
• least-privilege repository grants;
• separate read, append, retention, and administrative permissions;
• AEAD for all repository objects;
• signed snapshot and journal records;
• anti-rollback checkpoints anchored in local trusted state and optionally external witnesses;
• safe parser limits and bounded allocations;
• secret redaction by type, not string convention;
• dependency pinning and vulnerability scanning;
• signed releases and reproducible builds;
• secure auto-update with rollback protection;
• repository-server rate limiting and quotas;
• audit trail for destructive operations;
• restore to a quarantine path by default for untrusted historical content.

A formal threat model should be maintained as a versioned project document before the first beta.

## 18. Testing strategy

### 18.1 Unit and property testing

• canonical serialization round trips;
• segment-boundary determinism;
• blob parsing and corruption detection;
• retention invariants;
• path normalisation and collision handling;
• encryption nonce uniqueness;
• state-machine idempotency;
• object reachability;
• restore-plan determinism.

### 18.2 Storage contract tests

Every provider runs the same contract suite covering:

• conditional creation;
• range reads;
• interrupted upload;
• listing pagination;
• duplicate writes;
• stale metadata;
• eventual visibility simulations;
• deletion batching;
• retries and throttling;
• checksum mismatch;
• credential expiry;
• multipart abandonment and cleanup.

### 18.3 Interruption testing

Terminate the process or connection after every meaningful persistence step:

• while writing blob spool;
• during upload;
• after blob but before index;
• after index but before snapshot;
• during checkpoint compaction;
• during blob compaction;
• during tombstone publication;
• during restore;
• during legacy archive import.

After restart, all published snapshots must remain readable and operations must resume or roll forward safely.

### 18.4 Corruption testing

Inject:

• bit flips;
• truncated blobs;
• missing index deltas;
• missing blobs;
• reordered listings;
• replayed snapshots;
• forged object IDs;
• duplicated journal sequences;
• stale checkpoints;
• malformed legacy records.

The system must identify the smallest affected scope and, where replicas exist, heal without data loss.

### 18.5 Scale testing

Minimum target test profiles:

• 10 million files;
• 100 million file versions;
• multi-petabyte logical repositories through generated fixtures;
• very deep paths;
• millions of tiny files;
• multi-terabyte sparse files;
• high-churn VM/database-like files;
• 100 concurrent source devices;
• high-latency and low-bandwidth peers;
• object stores with request throttling;
• metadata cache rebuild from remote repository only.

A repository must not require loading all paths or versions into memory.

### 18.6 Conformance suite

Publish:

• repository fixture repositories;
• known keys and expected plaintext for test-only vectors;
• valid and invalid objects;
• format upgrade fixtures;
• wire-protocol transcripts;
• third-party reader requirements;
• deterministic cross-platform path cases.

────────

## 19. Performance objectives

Initial engineering targets, to be validated through benchmarks:

• bounded memory configurable independently of repository size;
• streaming operation for all file sizes;
• initial local backup capable of saturating typical consumer storage without excessive CPU;
• incremental scan proportional primarily to changed entries when journals are healthy;
• cloud uploads use blobs large enough to avoid request amplification;
• restore can fetch blob ranges rather than downloading unrelated whole blobs where provider support allows;
• local cache rebuild can proceed incrementally and support restore before full completion;
• peer transfer resumes from verified boundaries;
• background activity observes configurable CPU, disk, network, and time windows;
• no global metadata rewrite for each snapshot.

────────

## 20. Versioning and compatibility

Version independently:

• repository format;
• blob format;
• metadata schema;
• peer protocol;
• recovery-kit format;
• local configuration schema;
• Legacy importer compatibility.

Rules:

• readers advertise supported feature sets, not only a single integer version;
• unknown required features cause safe refusal;
• unknown optional fields are preserved or ignored according to specification;
• upgrades are append-only where possible;
• repositories can contain multiple blob/object generations;
• format migration is resumable and never destroys the last readable generation;
• emergency recovery tooling for each major format remains downloadable and buildable;
• deprecation requires a published migration path and support window.

## 21. Delivery roadmap

### Phase 0 — Archive engine vertical slice

Goal: Build the archiving engine first and prove that files can be segmented, compared, encrypted, packed into configured-size blobs, indexed, rebuilt, and restored without higher application layers.

Deliverables:

• architecture decision records and threat model;
• versioned configuration schemas for segment size, blob size, compression, encryption, concurrency, and spool behaviour;
• streaming fixed-segment reader and cryptographic segment hasher;
• prior-version segment comparison and unchanged-segment reuse;
• compression policy and supported codec profile;
• independently authenticated segment-record encryption;
• config-driven blob assembler, durable spool, sealing, and recovery footer;
• immutable file-version manifest encoding;
• local SQLite catalogue with segment and blob indexes;
• immutable index-delta and checkpoint prototype;
• local filesystem object store;
• catalogue deletion and normal/forensic rebuild tools;
• low-level CLI commands: archive, inspect-blob, inspect-manifest, rebuild-index, verify, and restore-file;
• deterministic format fixtures and interruption/corruption harnesses; and
• benchmarks across segment sizes, blob sizes, encryption profiles, compressible/incompressible data, large files, and high version counts.

Exit criteria:

• a multi-terabyte logical file can be processed with bounded memory and span many blobs;
• changing one fixed segment writes only that segment and a new file-version manifest;
• configured blob targets are respected without splitting segment records;
• every segment and complete restored file are cryptographically verified;
• interrupted blob construction or publication cannot expose an incomplete committed file version;
• the local catalogue can be deleted and rebuilt from checkpoint/deltas;
• a forensic rebuild succeeds using blob recovery footers and manifests after all global index objects are removed;
• an independently written reader can parse public fixtures; and
• one representative legacy file version can be streamed into this same archive pipeline.

### Phase 1 — Snapshot and local repository MVP

Goal: Build filesystem capture, immutable directory/snapshot manifests, and reliable local restore on top of the proven archive engine.

Features:

• cross-platform filesystem scanner;

• repository inspector;

Exit criteria:

• cross-platform directory backup and point-in-time restore;

• complete rebuild without the local database;
• restore can begin during partial catalogue rebuild; and

### Phase 2 — Peer-to-peer backup

## 23. Major risks and mitigations

|Risk|Consequence|Mitigation|
|----|-----------|----------|
|Repository format designed too early|Long-term compatibility burden|Prototype, publish draft, solicit review, freeze only after conformance tests.|
|Multi-writer inconsistency|Unreadable snapshots or lost data|Immutable objects, writer journals, explicit publication order, generation checkpoints.|
|Local cache becomes authoritative|Recovery failure after cache loss|Rebuild tests in CI; repository-only recovery tool.|
|Object-store request amplification|High cost and poor performance|Configured-size blob objects; batch indexes; range reads; provider metrics.|
|Unsafe pruning|Permanent data loss|Generation cut-offs, grace periods, tombstones, dry runs, interruption tests.|
|Key loss|Repository permanently unreadable|Mandatory recovery-kit workflow and recovery drill.|
|Key compromise|Data disclosure or deletion|Key hierarchy, scoped grants, destination retention floors, rotation.|
|Legacy format variation|Failed or inaccurate imports|Inspector, compatibility matrix, provenance, no silent fallback.|
|Importer licensing/provenance|Project legal exposure|Isolated package, legal review, clean-room implementation where required.|
|Filesystem semantic differences|Restore collisions or lost metadata|Capability records, collision planning, explicit degradation reports.|
|Public relay/discovery abuse|Cost and service disruption|Optional self-hosting, quotas, rate limits, minimal retained metadata.|
|Consumer UI hides degraded state|False confidence|Show last verified recovery point and destination-specific health.|

## 24. Definition of done for the first major release

FallbackPlan 1.0 should not be declared complete until:

• Windows, macOS, and Linux agents create and restore native snapshots;
• one computer can back up directly to another without a project-operated cloud service;
• Azure Blob and Amazon S3 repositories pass shared provider contract tests;
• all metadata and file content are encrypted before leaving the source trust boundary;
• a repository can be restored from a clean machine using only repository access and a recovery kit;
• deleting the local database/cache does not lose repository history;
• interruption tests cover snapshot publication, replication, restore, and maintenance;

• safe retention and pruning are implemented with dry-run and grace-period support;
• repository and peer protocol specifications are public;

• signed release artifacts and a standalone recovery tool are available;
• user documentation explains what is and is not protected;
• external security and format reviews have been completed;
• Legacy import is either released with a narrow verified compatibility matrix or clearly retained as preview—not broadly claimed.

## 27. Recommended architectural decision

Proceed with FallbackPlan as a snapshot-based backup repository with repository replication, rather than a folder-sync product with versioning added later.

The first vertical slice should be:

> Select a folder → create an encrypted immutable snapshot → store it locally → delete all local cache state → reconstruct the repository index → restore and verify the folder on a clean machine.

The second vertical slice should be:

> Pair two computers → transfer the repository snapshot to the destination → destroy the source installation → restore solely from the destination and recovery kit.

Only after these are reliable should Azure, S3, retention pruning, and legacy conversion be layered on. This sequence makes recoverability—not feature count—the foundation of the project.
