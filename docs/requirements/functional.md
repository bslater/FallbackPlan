# Functional requirements

**Status:** draft · **Supersedes:** [original proposal](../review/2026-08-original-proposal.md) §3.4 · **Traceability:** [`traceability.md`](traceability.md)

---

Each requirement states an **observable acceptance criterion**. The original set contained a number of requirements that could not fail a test — "where beneficial", "shall be configuration driven", "trustworthy metadata" ([M5](../review/2026-08-architecture-review.md#m5--most-requirements-are-not-testable-as-written-and-the-promised-traceability-does-not-exist)) — and those have been given thresholds or observable outcomes.

Requirements marked **[changed]** differ materially from the original; **[new]** did not exist. The original wording of every changed requirement is quoted in the [review](../review/2026-08-architecture-review.md).

---

## Archive engine

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-ARCH-001 **[changed]** | The engine shall segment each regular file according to the backup set's segmentation profile. `fixed-v1` produces equal-length segments at fixed offsets; only the final segment may be shorter. `cdc-v1` produces content-defined boundaries within configured min/target/max bounds. | Given a byte string and a profile, segmentation is deterministic and reproducible across platforms and runs. |
| FR-ARCH-002 | Segmentation, hashing, compression, encryption, and packing shall operate as a bounded-memory stream. | Peak RSS while processing a 2 TiB file stays within the NFR-PERF-001 bound. |
| FR-ARCH-003 | The engine shall compute a cryptographic plaintext content identifier for each segment before encryption. | Content identifier is reproducible from plaintext alone. |
| FR-ARCH-004 | Unchanged segments shall be reused by reference rather than re-stored. | Modifying one segment of an *n*-segment file writes exactly one new segment record. |
| FR-ARCH-005 **[changed]** | New or changed segments shall be compressed, encrypted independently, authenticated, and appended to a blob. A segment shall be stored uncompressed when compression saves less than the configured fraction of its length (default 5%). The choice shall be recorded per record. | Incompressible input yields records marked uncompressed; compressible input yields records marked compressed. Both restore correctly. |
| FR-ARCH-006 | A file version may reference segments in any number of blobs; blob boundaries shall not affect file semantics or restore order. | A file spanning ≥ 100 blobs restores byte-identically. |
| FR-ARCH-007 **[changed]** | Target and maximum blob sizes shall come from a versioned write profile, be validated against the store's reported `MaximumObjectSize`, and be recorded in the policy manifest for each snapshot. | A profile exceeding a provider limit is rejected at configuration time with a named reason, not at write time. |
| FR-ARCH-008 | Encryption algorithm, key generation, and parameters shall be selected from supported profiles and recorded per encrypted record. Unsupported or unsafe combinations shall be rejected. | An unapproved suite is rejected at configuration time. |
| FR-ARCH-009 | Every encrypted segment record shall be independently authenticated. | Corrupting one record leaves all other records in the same blob readable and verifiable. |
| FR-ARCH-010 **[changed]** | File versions shall be reconstructed from ordered segment references containing logical offset, logical length, and **object identifier**. A segment reference shall contain **no blob identifier and no physical offset**. | A manifest encoding containing a blob ID or physical offset fails format validation. After blob compaction, every pre-existing manifest resolves without modification. |
| FR-ARCH-011 **[amended]** | Interrupted blob construction shall resume from a verified spool checkpoint or be safely abandoned, never becoming visible as a committed object. The checkpoint shall store the **sealed record bytes** and every parameter that could vary on resume — blob salt, writer ID and blob counter, segmentation profile, compression codec and version, encryption profile. Resume shall re-emit stored bytes, never recompute them; any parameter mismatch shall force a restart. | Kill-and-resume at any record boundary produces a byte-identical blob. Resume after a compression codec **version change** re-emits stored bytes or refuses to resume — it never recompresses under an already-used ordinal. Kill-and-restart produces a different blob salt. |
| FR-ARCH-012 | A sealed blob shall be immutable, and its authenticated recovery footer shall contain sufficient metadata to inspect it and rebuild index entries. | Every record in a blob is locatable, decryptable, and verifiable from the blob and repository keys alone. |
| FR-ARCH-013 | The engine shall correctly represent empty files, sparse extents, files smaller than one segment, and files spanning many blobs. | Each case round-trips byte-identically, and sparse extents restore without materialising zero payload. |
| FR-ARCH-014 **[changed]** | The format shall define both `fixed-v1` and `cdc-v1` segmentation profiles in v1. The profile shall be recorded per file version and selectable per backup set. Format v1 shall not be frozen until both are benchmarked against a representative corpus and the results published. | Both profiles have conformance fixtures. The benchmark report exists before freeze. |

## Manifests, indexes, and catalogue

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-MAN-001 | Authoritative manifests and indexes shall be immutable repository objects. No local database shall be required to interpret or restore a committed snapshot. | Restore succeeds on a machine with no catalogue and no prior state. |
| FR-MAN-002 **[amended]** | Each instance shall maintain a local transactional catalogue for fast lookup. It shall be disposable and fully rebuildable from repository objects. **[amended]** A catalogue found missing, or discarded because another schema version or repository wrote it, shall be rebuilt from the repository before anything is answered from it; a rebuild that could not read every record it needed shall be tried again at the next open rather than taken for complete ([ADR-0010](../adr/0010-local-store-separation.md) Amendment 4). | Deleting the catalogue and rebuilding reproduces equivalent lookup results. A set whose catalogue was deleted while the service was stopped, or stamped by an older schema, lists its snapshots and their files when the service next opens it; one rebuilt while its direct-ship destination was away is rebuilt again at the next open, and reading the set's blobs to rebuild it creates nothing at a destination that holds no replica of it. |
| FR-MAN-003 **[changed]** | Each file version shall have an immutable manifest containing path identity, metadata, logical length, ordered segment references (logical facts only, per FR-ARCH-010), parent-version reference where known, and a whole-file verification hash. | Manifest bytes are unchanged by any maintenance operation. |
| FR-MAN-004 | Trees and snapshots shall reference file-version manifests through immutable sharded tree objects. No snapshot shall require a monolithic repository-wide manifest. | No single manifest's size grows with repository or history size. |
| FR-MAN-005 | The catalogue shall resolve a path within a snapshot without scanning unrelated snapshots, trees, blobs, or records. | Resolution meets the NFR-PERF-004 latency target at the stated scale. |
| FR-MAN-006 **[amended]** | The catalogue shall resolve a content identifier within its segmentation profile, dedup trust domain, and **writer attribution** to determine whether a reusable segment exists. Writer attribution shall be recoverable from index delta `writer_id` during a rebuild. | Lookup meets the NFR-PERF-010 target. After a catalogue rebuild, `device` mode still identifies which segments this device wrote. |
| FR-MAN-007 | Every sealed blob shall include an authenticated recovery footer listing each record's object identifier, physical offset, stored length, logical length, and encoding profiles. | Forensic rebuild reconstructs all index entries from footers alone. |
| FR-MAN-008 **[changed]** | Index deltas shall be immutable and published only after their blobs are durable. Each delta shall carry `(writer_id, sequence, predecessor_delta_id)` with strictly increasing, gapless per-writer sequence. Checkpoints shall enumerate the exact delta IDs they subsume and the per-writer high-water sequence. | A reader detects a missing sequence number rather than assuming completeness. **[amended]** A delta above a checkpoint's watermark is applied whenever a listing returns it, so a checkpoint never hides one; a delta a listing omits is detected as a gap once a later number of its writer is seen. **[amended]** Every delta a writer publishes is one a reader can open: none exceeds the 16 MiB metadata object bound (specification 00 §8). A publication whose entries would exceed it publishes several deltas, cut at blob boundaries so each blob is covered by exactly one, and the publisher refuses an index object over the bound rather than write it. **[amended]** From format 5 a checkpoint carries the deltas it subsumes as their stored objects, beside their identifiers, and nothing of its own; a reader reads a carried delta from the checkpoint, exactly as from its key, and acts on no watermark ([ADR-0097](../adr/0097-format-5-a-checkpoint-carries-its-deltas.md)). A delta no checkpoint carries is applied whenever a listing returns it. |
| FR-MAN-013 **[amended]** | Two checkpoints published at the same generation shall both be retained and both applied. Convergence shall rest on explicit precedence, not on commutativity. | Applying either order, or both, yields identical catalogue state — including when one delta relocates an object identifier another delta already mapped. |
| FR-MAN-015 **[new]** | Every index entry shall carry the generation at which it was published, and shall declare whether it is an insertion or a **supersession**. For a given object identifier the highest generation shall win, with a documented deterministic tie-break. **[amended]** An entry carries its generation through the delta or checkpoint that publishes it, which every entry in that object shares. **[amended]** From format 4 a delta's generation is its index generation: one more than the highest its writer had seen, which every delta a format-4 writer publishes carries and an entry ranks by before writer and sequence ([ADR-0096](../adr/0096-format-4-an-index-generation-per-delta.md)). | After compaction relocates an object, a reader applying the pre-compaction delta last still resolves to the new location, never to the tombstoned blob. **[amended]** This holds whichever writer published the relocation, and whichever published the entry it relocates. **[amended]** At format 4 it holds by rank: a compaction under the lower of two writer ids stands, is not declined, and is not undone by the next pass. |
| FR-MAN-016 **[new]** | A writer that skips a journal sequence shall publish a signed **void delta** at that number. Readers shall treat a gap as unresolved until the delta or its void record appears, and shall surface it as a damage finding after a bounded number of generations rather than blocking. **[amended]** A number is not a gap when a journal record carries it, or when an intent or extension names a blob that embeds it, whether or not that blob still exists. Only records that open and verify count. The product's own index loads shall apply this accounting. **[amended]** The bounded number is counted per gap: from format 4, in index generations since the first delta the gap's writer published above it. The product's readers judge a gap at eight. | A writer that crashes between preparing and publishing a delta does not permanently block readers. Silence is never interpreted as an empty delta. **[amended]** Once the generations a reader waits through have passed, a backup's journal records and blobs are not reported as damage. Neither are the blobs of a backup that died after its uploads, once a collector has removed them. A dropped delta is still reported, and an object planted under a journal key accounts for nothing. **[amended]** A gap is reported once eight index generations have passed since its writer's next delta, whether that writer is still publishing or has stopped and another writer is. A gap in format-3 history is not aged by the format-4 deltas after it. |
| FR-MAN-018 **[new]** | The policy manifest shall record the backup set's shape — its roots' paths and labels, its name and its schedule — as optional keys, so that an archive can re-declare the set that wrote it; a manifest that records no shape shall encode byte-identically to one written before the keys existed, and a reader shall tolerate their absence while still refusing an unknown key. | A manifest with the shape round-trips; one without encodes the nine-key map unchanged; a recorded root carrying an unknown key is refused; a service run's newest policy manifest carries the configured roots, name and schedule. |
| FR-MAN-017 **[amended]** | A delta shall be retired only when named by a checkpoint that no live checkpoint at or above its generation contradicts. Retirement shall use tombstone-and-grace. **[amended]** From format 5, a delta shall be deleted from a store only when, at that store, a checkpoint carries a copy of it that opens and is byte for byte the object at its key, that checkpoint's writer has published there since, and the store's listing reflects every completed put. Checkpoints shall not be retired, and no tombstone is written. A reader shall list the deltas before the checkpoints and look for a listed delta it finds gone in a second listing of the checkpoints. A replica shall not retire a delta the store it is copied from still lists ([ADR-0098](../adr/0098-a-store-retires-what-its-own-checkpoints-carry.md)). **[amended]** A peer, which its owner cannot delete from, shall retire under a person's reclaim grant: the owner judges the peer's replica by the same rule from the peer's own copies, and names only what passes in the drop list it signs ([ADR-0098 Amendment 1](../adr/0098-a-store-retires-what-its-own-checkpoints-carry.md#amendment-1-2026-10--a-peer-retires-under-a-persons-grant)). | With concurrent checkpoints naming different delta sets, no reader loses index entries for a delta retired on another checkpoint's authority. **[amended]** A load racing a retirement, before either listing or between them, applies the retired delta from its carrier; and a store keeps a delta whose carrier is unsettled, absent, damaged or names other bytes. **[amended]** A person's retention run drops at a peer the deltas its settled checkpoints carry, leaves every checkpoint there, and the peer's replica alone still restores what they indexed. A peer keeps a delta whose carrier it does not hold, though the owner's own plane let it go, and a delta the owner's plane still lists; and a run whose peer attests history the owner's state has never heard of drops no delta there. |
| FR-MAN-019 **[new]** | A repository shall be movable to a newer format version without rewriting or re-seeding anything it already holds, by an append-only signed record rather than by a rewritten descriptor — which no copy would accept. The newer format shall take effect at the next sealed object, leaving everything already sealed readable exactly as it is; every copy shall learn of the move through the ordinary replication paths, needing no protocol change; and the record shall be undeletable by a retention instruction. A record whose signature does not verify shall be ignored rather than treated as damage. | A set upgraded while the service runs seals the newer format on its very next backup and still restores everything written before it, byte for byte. The record reaches a local-path destination and a peer replica on the next reconciling pass with no protocol change, and a retention instruction naming it is refused whole. A set already at the latest version, a set with no archive yet, and a set with a run in progress are each refused by name, writing nothing. |
| FR-MAN-009 **[amended]** | The engine shall support normal rebuild (checkpoint plus deltas) and forensic rebuild (blob footers plus snapshot roots). | Both succeed; forensic rebuild succeeds after every index object is deleted. **[amended]** A normal rebuild of a format-5 repository reads its checkpoints and fetches only the deltas none carries, and reaches the index a rebuild from the deltas alone reaches: every entry ranked, credited and committed to exactly as from its delta ([ADR-0097](../adr/0097-format-5-a-checkpoint-carries-its-deltas.md)). |
| FR-MAN-010 | Listing and restore shall become available incrementally during rebuild, as soon as the required dependency graph is known. | A snapshot restores before full repository rebuild completes. |
| FR-MAN-011 | Rebuild shall verify signatures, authenticated metadata, record bounds, duplicate and conflicting mappings, generation ordering, and references to missing blobs. | Each injected fault class is detected and named. |
| FR-MAN-012 | The engine shall distinguish catalogue corruption, missing index objects, missing blobs, corrupt records, and unreachable orphans, reporting which snapshots and file versions are affected. | Each fault class produces a distinct report naming the affected scope. |
| FR-MAN-014 **[new]** | Rebuild shall never rewrite or repair repository objects. | A rebuild run leaves every repository object byte-identical. |

## Deduplication trust

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-DED-001 **[new]** | The repository shall support dedup trust domains `device`, `repository`, and `repository-unverified`. | Each is selectable and recorded in the policy manifest. |
| FR-DED-002 **[amended]** | `repository` shall be the default. In a single-writer repository it shall behave identically to `device` at no additional cost. `device` shall remain available as a hardened opt-in. **[amended]** `device` is the default, and `repository` is refused by name, because no writer holds the content key its verification needs ([ADR-0006](../adr/0006-object-identifiers-and-dedup-trust-domains.md#trust-domains--new)). Under `device` a writer shall reference an object only where a live entry of its own locates it, whichever writer's entry a reader resolves the object to ([ADR-0006](../adr/0006-object-identifiers-and-dedup-trust-domains.md#amendment-2026-10--a-devices-own-copy-is-one-it-holds-not-only-one-that-wins)). | A fresh single-device repository performs no verification reads. A multi-device repository deduplicates across devices with verify-on-reuse. **[amended]** Under `device`, a second writer stores a changed file's unchanged segments once, whichever way its id sorts against the first writer's, and a copy whose blob is known deleted is not its own. |
| FR-DED-003 **[amended]** | In `repository`, a segment written by another writer shall be fetched, decrypted, and its content identifier confirmed before being referenced. | A segment whose stored plaintext does not match its claimed content identifier is never referenced, and the mismatch is reported as a damage finding naming the object. Verification outcomes are catalogue state and are **not** required to survive a rebuild. |
| FR-DED-004 **[new]** | `repository-unverified` shall require explicit acknowledgement recording that a faulty or hostile writer can corrupt other devices' backups. | It cannot be enabled without the acknowledgement. |

## Snapshots

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-SNP-001 **[amended]** | A snapshot shall be committed to a replica only after every object it references is durable **in that replica**. Commit is per-replica; replication to other destinations is independent state. | For a staging set, a destination being offline delays policy compliance but does not prevent local commit. For a direct-ship set ([ADR-0046](../adr/0046-direct-to-destination-publication.md)) there is no local replica to commit to: the snapshot commits at each destination that completed the run, and FR-DEST-015 governs the case where none could. |
| FR-SNP-002 | File deletion shall create new snapshot state and shall not directly delete older file versions or segment records. | Prior versions remain restorable after a deletion snapshot. |
| FR-SNP-003 **[new]** | Each `(snapshot, destination)` pair shall carry independent replication status: `pending`, `replicating`, `durable`, `verified`, `degraded`. **[amended]** A pass that proves what it copied shall record the copy and its proof in one ledger write, so a copy that pass proved is never reported `durable`. | Status is queryable per destination and drives policy evaluation. **[amended]** No ledger write made by a pass that proved what it copied calls the destination in sync ahead of that proof, so no reader sees the snapshot `durable` rather than `verified`. |
| FR-SNP-004 **[amended]** | A write-intent record naming the blobs a job will create shall be durable **before** those blobs are uploaded, and retired when the work completes. This shall apply to **every** component that creates a blob, including the garbage collector during compaction. | No blob is uploaded without covering intent, verified for backup writers and collectors alike. Garbage collection never deletes an intent-covered blob. |
| FR-SNP-005 **[new]** | An intent shall expire only when **both** the repository has advanced past its `expiry_generation` **and** its writer-declared `declared_max_duration` has elapsed with a configured skew margin. | A slow writer's intent is not expired by other writers' activity advancing generations. An audited administrative force-expire exists. |
| FR-SNP-006 **[new]** | Blob identifiers shall be writer-allocated and opaque, not content-derived, so a writer can name them in an intent before creating them. | A blob identifier is allocatable before the blob is sealed. Record identifiers remain content-derived and keyed. |
| FR-SNP-007 **[new]** | Each replica shall declare a failure domain (`same-volume`, `same-machine`, `same-site`, `independent`). A snapshot shall be reported `protected` only when at least one replica outside the source's failure domain holds it; one held only within the source's domain is `captured`. | A repository configured on the source volume reports `captured`, never `protected`. First-run warns when the only destination shares a failure domain with the source. |
| FR-SNP-008 **[new]** | A backup set shall capture one or more source folders into a single snapshot. With several, each folder shall appear at the snapshot root as a directory named by a label persisted in configuration, capture rules shall be evaluated against label-prefixed subjects, and a backup shall refuse — recoverably, naming every missing folder — rather than capture with any folder absent. A single-folder set's snapshot shall be byte-identical to the pre-multi-root shape. | A two-folder set publishes one snapshot whose top level is the two labels in raw-byte order and restores as `<output>/<label>/…`; a label-prefixed exclude prunes only its own folder's subtree; a run with one folder unmounted records a recoverable failure naming it and publishes nothing; a one-folder set round-trips with no synthetic root. |

## Disaster recovery

The rows above answer the case where the *store* survives and the machine's local state does not: the passphrase alone opens it ([ADR-0060](../adr/0060-the-passphrase-is-the-recovery-credential.md)), and the recovery kit that once answered it is withdrawn. This section answers the harder one: the machine itself is gone — ransomware, theft, fire, or a rebuild from bare metal after malware — and the only surviving copy is a replica at a destination. Durable local state is not a cache and does not come back with it ([architecture 00](../architecture/00-overview.md)), so the recovering device is a **new** device identity as far as every destination is concerned ([ADR-0010](../adr/0010-local-store-separation.md)). The ceremony that answers it is [ADR-0053](../adr/0053-peer-claim-and-configuration-recovery.md); [ADR-0070](../adr/0070-replica-claim-after-total-loss.md) reached the same conclusion independently and is superseded by it.

FR-DR-005 and FR-DR-009 were left **unbuilt**, and deliberately so. They are the two properties of the
disaster-recovery review that the claim ceremony this repository *did* build did
not have. **FR-DR-005 is now built** ([ADR-0053 Amendment 4](../adr/0053-peer-claim-and-configuration-recovery.md#amendment-4-2026-09--a-claim-is-held-until-the-destinations-operator-acknowledges-it)):
a claim that moves an attribution is held, the destination raises a notice, and
the claimant's retention instructions are refused, deleting nothing, until the
destination's operator acknowledges the claim. That refusal answers a
different question from the reclaim-signature ones of
[ADR-0055](../adr/0055-reclaim-authority.md) and
[ADR-0059](../adr/0059-session-bound-deletion-authority.md): not who signed the
instruction, but whether the destination's operator has acknowledged who is
now asking, and the claimant holds the key that signs. **FR-DR-009 is now
built too** ([ADR-0061 Amendment 2](../adr/0061-adopt-a-destinations-archives.md#amendment-2-2026-09--a-recovered-configuration-is-confirmed-before-it-takes-effect)).
Adoption first shows the configuration the archive recorded: each root's
recorded path, flagged where it does not resolve on this machine, and the
retention the set would delete by. It takes effect only with the
confirmation that preview answered. An adoption without one is refused by
name, one the archive has moved on from since is refused as changed, and a
root can be re-pointed when the person confirms. Both rows have proof
obligations now that the product claims them.

**FR-DR-006 arrived with its work.** The review also found that the repository
did not carry the set's **retention policy** as part of its recorded shape, so a
machine that reconstructed a set from the repository alone recovered everything
about it except what it was allowed to delete. That was recorded here as owed,
because the row that carries it should arrive with the work. It has: the policy
manifest records the set's own retention beside its name, roots and schedule, and
adoption re-declares it ([ADR-0061 Amendment 1](../adr/0061-adopt-a-destinations-archives.md#amendment-1-2026-09--the-sets-own-retention-is-recorded)).


## Write-only repositories

Every repository ([ADR-0042](../adr/0042-write-only-repositories.md); the only format since [ADR-0014 Amendment 1](../adr/0014-format-versioning-and-stability.md#amendment-1-2026-09--format-1-withdrawn-before-freeze)) severs writing from reading: the service seals file contents to an asymmetric public key and holds nothing that opens them.

| FR-SVC-014 **[new]** | When every pool slot is busy and a strictly higher-ranked backup arrives, the lowest-ranked running backup that can yield shall be **suspended at a file boundary** — its in-memory state held, its slot freed — and shall **resume where it stopped**, not restart, when a slot frees; a freed slot resumes suspended work before starting new work of equal standing. Suspension shall be bounded: a run paused past a configured age shall self-cancel to the interruption-safe re-run path, and shutdown shall degrade a suspended run the same way. The suspended state shall be visible as a live, non-terminal job state. | The incomer runs while the preempted backup is suspended, and the preempted backup then completes committing one whole snapshot with nothing re-scanned; a client awaiting the job keeps waiting through the suspension; shutdown while suspended cancels cleanly and the next run publishes intact. |
| FR-SVC-015 **[new]** | Saving a new backup set shall queue its first backup immediately — a person clicking Save is asking for a backup, not a schedule entry — and the reply shall name the queued job. A set gaining a destination shall mark the pair owed its full copy (FR-DEST-014) and queue that destination's seed immediately. | A new set's upsert reply names its queued first backup and the destination populates without waiting for a schedule; a gained destination begins seeding without operator action. |
| FR-SVC-016 **[new]** | Every process of the installation — the service, the web console, and the CLI — shall resolve the same default state location when none is named: the machine-wide data directory (`%ProgramData%\FallbackPlan`, `/var/lib/fallbackplan`, `/Library/Application Support/FallbackPlan`), falling back to the user profile only where that cannot be created, overridable by environment variable and then by the path flags. A bare service invocation shall start on that installation, a path-less console or CLI verb shall connect to it, and an unusable path (default or named) shall be refused with a stated reason, never a stack trace. | `fallbackplan-agent` with no arguments starts the service; `fallbackplan-web` with no arguments connects to it; a CLI verb naming no repository is answered by that service with no passphrase; the environment overrides redirect a whole session together; a state directory that cannot be created or opened is refused with a message naming the problem. |
| FR-SVC-017 **[amended]** | The service shall reconcile its job journal at start: no record shall claim to be running in a process that is not running it — unfinished rows shall settle as recoverable failures with a durable notice raised. Cancelling a run whose record is unfinished but which is no longer live shall settle the record rather than refuse, and cancelling a backup that has not yet started shall settle its record at the command rather than when a worker reaches it ([ADR-0029](../adr/0029-pipeline-and-service-concurrency.md) Amendment 5). Deleting a backup set shall defer only to runs the scheduler is actually running. An owner shall be able to command a service restart from the console and the CLI — an in-process recycle, identical on every platform — refused to operators by name, refused from the remote binding, refused before setup, and refused where no host can recycle ([ADR-0049](../adr/0049-service-lifecycle-hygiene.md)). | A journal carrying a mid-run row from a dead process starts with the row settled and one notice; cancel on a stuck record acknowledges and settles it; a cancel of a backup queued behind another reads Cancelled in the journal at once, while the running one carries on, and a second cancel is not found; a set with only an orphaned record deletes; the console shows the restart control to the owner alone behind a typed confirmation, the CLI verb is `restart`, and the shipped host recycles in the same process — two listens, no exit — with every session signed out. |
| FR-SVC-018 **[new]** | A settled run shall be able to say what it did. Its terminal numbers — files seen, done, reused and failed, bytes read and newly stored, and the counted plan — shall persist on its journal row at every terminal transition, failed and cancelled runs included, additively (a pre-existing row reads back with none, never as corrupt), while the journal remains sacrificial on [ADR-0027 §2](../adr/0027-services-scheduling-status-telemetry.md)'s terms. The details shall be served from the repository on demand: what the run changed against the set's previous snapshot (exact counts, bounded samples, agreeing with the snapshot browser's comparison by construction), and its capture failures — each path with its typed reason and the scanner's own words — from the error manifest. A run that committed no snapshot shall be refused those details by name. The job listing shall accept a bound, newest rows first ([ADR-0050](../adr/0050-completed-run-record-and-drill-down.md)). **[amended]** Those details name the backup's files, so they are served only through a source of the run's set the passphrase unlocked (FR-WOR-007, [ADR-0089](../adr/0089-a-backups-file-names-need-the-passphrase.md)). | Clicking a completed job in the console opens its report: counts, bytes, duration, capture status, with "what changed" and "failures" one click deeper and the snapshot browser beside them; `jobs <id> --changes --failures` answers the same from the CLI; a partial run's row carries the counts its detail string omits; a cancelled run's row records how far it got. |
| FR-SVC-019 **[new]** | A running service shall outlive a scheduler pass it cannot run. When a pass fails to read its configuration or its state, the service shall keep its listeners and serve every command, report the failure where a client will see it, and try again at the next tick; the first pass that runs again shall clear the report. Start-up is unchanged: a configuration that will not load when the service starts is still refused by name ([NFR-OPS-003](non-functional.md)). | With the service running, a `config.json` that no longer parses leaves it running and answering; each failed pass names the file, and a notice stands until a pass runs again. Restored, the next pass runs, the notice is resolved, and a stop is still a clean exit. |
| FR-SVC-020 **[new]** | An edit made through the service shall change only what it names. A field an upsert leaves out — because the client predates it, or because it has no wire field at all and lives in the configuration file alone — shall keep its stored value ([ADR-0037](../adr/0037-configuration-over-the-command-contract.md) §1). | Re-saving a destination from the console, which carries neither its drill cadence nor its transfer limit, leaves both in the file; every field a destination persists is either carried by its descriptor or kept from the stored declaration, and a field that is neither fails a test until it is one or the other. |
| FR-SVC-021 **[new]** | The installation's own settings — the background window, the background read limit and the backup pool's width — and a destination's transfer limit and drill cadence shall be readable and settable through the command contract ([ADR-0037](../adr/0037-configuration-over-the-command-contract.md) Amendment 1), not only in the configuration file. A value shall be judged by the parser the configuration load uses and refused naming the setting, never the configuration file's path; a request shall apply whole or not at all; and each change shall say when it takes effect — the pool's width at the service's next start, with the running width reported beside the stored one until then. | A window set from the console or the CLI is in the file and on status at once; an unreadable rate is refused naming MiB/s, with the file byte-identical and none of the request's other values applied; a width of 3 saved on a service running 2 reports 3 stored and 2 running until a restart; an empty text or a zero clears a setting, and null keeps it. |
| FR-SVC-022 **[new]** | The console shall make a new backup set in steps: its name; what it backs up, with the selection filters that narrow it; and its destinations, each answered before the next; then its exclusions, its retention and its other settings, each of which may be left as it stands ([ADR-0037](../adr/0037-configuration-over-the-command-contract.md) Amendment 2). Nothing shall be saved before the walk's last confirmation. A step shall say a refusal the save would meet while that step's choice is being made, and hold until it is resolved. Editing an existing set shall keep its summary, with a dialog per section. | A new set's walk holds each required step until it is answered, a name another set already has included; Create is offered from the destinations step on and sends one upsert carrying every step; Back and the step indicator keep every step's answer; a destination on a root's drive is said on the destinations step, in the save's words, and holds it; an existing set opens on its summary. |

## User accounts and sessions

These are about **who is acting**, not about which process may connect. The
channel checks are unchanged: the local binding stays authenticated by the
operating system ([T-16](../threat-model.md)) and the remote binding stays
authenticated by pinned device pairing ([T-20](../threat-model.md), FR-SVC-004).
A password is never a new way to reach a service —
[ADR-0045](../adr/0045-client-authentication.md) §2.

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-USR-001 **[amended]** | An installation shall hold named user accounts, the first captured during first-run setup before setup completes. A password shall be refused where it is chosen — creation and change, never login — unless it is at least ten characters with an uppercase letter, two digits and a special character; the setup ceremony shall additionally refuse a password equal to the installation passphrase, compared by hash so the passphrase is not held. A client acting against a service shall identify itself as one of those accounts before issuing any command other than reading the service's description or logging in. | A fresh installation cannot complete setup without a first account; a password missing any rule is refused naming it, at the store so every creation path answers identically; the ceremony's account step will not enable Create User for the passphrase itself; a second console connecting to a set-up service can render a login screen and nothing else until it authenticates; every other verb is refused by name with how to log in. |
| FR-USR-002 **[new]** | A password shall be stored only as a memory-hard one-way hash with a per-account salt and its parameters recorded beside it, in the service's own state and never in the repository metadata plane. No password and no hash shall appear in any log record, any command result, or any diagnostic. | The stored form does not reveal the password and does not verify a different one; changing the password changes the salt; a full backup, restore and diagnostics sweep contains neither the password nor its encoded hash anywhere. |
| FR-USR-003 **[new]** | A successful authentication shall mint a session bound to the connection, with an idle timeout and an absolute expiry, listable and revocable at the service, held only in the running process. A restart shall end every session. | One authentication serves a connection's lifetime rather than one command; an idle session stops working without a new one being needed elsewhere; restarting the service requires everyone to log in again, and no session survives on disk. |
| FR-USR-004 **[new]** | The first account shall be the owner: it shall not be deletable and shall not be lockable out, and initially only it may create or remove accounts. Every account shall carry a role, so that narrower rights can later be granted without a migration. | Deleting the owner is refused by name; a second account cannot create a third; the stored form of every account carries its role from the first release, and reading an account written before any narrower role existed does not fail. |
| FR-USR-005 **[new]** | Repeated authentication failures for an account shall impose an increasing bounded delay and shall be recorded at warning with the account named. Nothing shall lock. | Five wrong passwords take visibly longer than one and the delay stops growing at its cap; the correct password still works immediately afterwards; no sequence of failures by anyone can deny an account its own backups. |
| FR-USR-006 **[new]** | The service process itself and the CLI's direct mode shall be unaffected: scheduled work shall run with no person present, and a direct-mode invocation holding the installation passphrase shall authenticate itself. Automation shall name a password by environment variable, never on a command line. | Scheduled backups run on a machine where nobody is logged in; `--direct` works with only the passphrase; a password given as a command-line argument is refused, and the named-variable form succeeds. |
