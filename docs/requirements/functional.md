# Functional requirements

**Status:** draft · **Supersedes:** [original proposal](../review/2026-08-original-proposal.md) §3.4 · **Traceability:** [`traceability.md`](traceability.md)

---

Each requirement states an **observable acceptance criterion**. The original set contained a number of requirements that could not fail a test — "where beneficial", "shall be configuration driven", "trustworthy metadata" ([M5](../review/2026-08-architecture-review.md#m5--most-requirements-are-not-testable-as-written-and-the-promised-traceability-does-not-exist)) — and those have been given thresholds or observable outcomes.

Requirements marked **[changed]** differ materially from the original; **[new]** did not exist. The original wording of every changed requirement is quoted in the [review](../review/2026-08-architecture-review.md).

---

## Archive engine

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-ARCH-001 **[changed]** | The engine shall segment each regular file according to the backup set's segmentation profile. `fixed-v1` produces equal-length segments at fixed offsets; only the final segment may be shorter. `cdc-v1` produces content-defined boundaries within configured min/target/max bounds. | Given a byte string and a profile, segmentation is deterministic and reproducible across platforms and runs. |
| FR-ARCH-002 | Segmentation, hashing, compression, encryption, and packing shall operate as a bounded-memory stream. | Peak RSS while processing a 2 TiB file stays within the NFR-PERF-001 bound. |
| FR-ARCH-003 | The engine shall compute a cryptographic plaintext content identifier for each segment before encryption. | Content identifier is reproducible from plaintext alone. |
| FR-ARCH-004 | Unchanged segments shall be reused by reference rather than re-stored. | Modifying one segment of an *n*-segment file writes exactly one new segment record. |
| FR-ARCH-005 **[changed]** | New or changed segments shall be compressed, encrypted independently, authenticated, and appended to a blob. A segment shall be stored uncompressed when compression saves less than the configured fraction of its length (default 5%). The choice shall be recorded per record. | Incompressible input yields records marked uncompressed; compressible input yields records marked compressed. Both restore correctly. |
| FR-ARCH-006 | A file version may reference segments in any number of blobs; blob boundaries shall not affect file semantics or restore order. | A file spanning ≥ 100 blobs restores byte-identically. |
| FR-ARCH-007 **[changed]** | Target and maximum blob sizes shall come from a versioned write profile, be validated against the store's reported `MaximumObjectSize`, and be recorded in the policy manifest for each snapshot. | A profile exceeding a provider limit is rejected at configuration time with a named reason, not at write time. |
| FR-ARCH-008 | Encryption algorithm, key generation, and parameters shall be selected from supported profiles and recorded per encrypted record. Unsupported or unsafe combinations shall be rejected. | An unapproved suite is rejected at configuration time. |
| FR-ARCH-009 | Every encrypted segment record shall be independently authenticated. | Corrupting one record leaves all other records in the same blob readable and verifiable. |
| FR-ARCH-010 **[changed]** | File versions shall be reconstructed from ordered segment references containing logical offset, logical length, and **object identifier**. A segment reference shall contain **no blob identifier and no physical offset**. | A manifest encoding containing a blob ID or physical offset fails format validation. After blob compaction, every pre-existing manifest resolves without modification. |
| FR-ARCH-011 **[amended]** | Interrupted blob construction shall resume from a verified spool checkpoint or be safely abandoned, never becoming visible as a committed object. The checkpoint shall store the **sealed record bytes** and every parameter that could vary on resume — blob salt, writer ID and blob counter, segmentation profile, compression codec and version, encryption profile. Resume shall re-emit stored bytes, never recompute them; any parameter mismatch shall force a restart. | Kill-and-resume at any record boundary produces a byte-identical blob. Resume after a compression codec **version change** re-emits stored bytes or refuses to resume — it never recompresses under an already-used ordinal. Kill-and-restart produces a different blob salt. |
| FR-ARCH-012 | A sealed blob shall be immutable, and its authenticated recovery footer shall contain sufficient metadata to inspect it and rebuild index entries. | Every record in a blob is locatable, decryptable, and verifiable from the blob and repository keys alone. |
| FR-ARCH-013 | The engine shall correctly represent empty files, sparse extents, files smaller than one segment, and files spanning many blobs. | Each case round-trips byte-identically, and sparse extents restore without materialising zero payload. |
| FR-ARCH-014 **[changed]** | The format shall define both `fixed-v1` and `cdc-v1` segmentation profiles in v1. The profile shall be recorded per file version and selectable per backup set. Format v1 shall not be frozen until both are benchmarked against a representative corpus and the results published. | Both profiles have conformance fixtures. The benchmark report exists before freeze. |

## Manifests, indexes, and catalogue

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-MAN-001 | Authoritative manifests and indexes shall be immutable repository objects. No local database shall be required to interpret or restore a committed snapshot. | Restore succeeds on a machine with no catalogue and no prior state. |
| FR-MAN-002 | Each instance shall maintain a local transactional catalogue for fast lookup. It shall be disposable and fully rebuildable from repository objects. | Deleting the catalogue and rebuilding reproduces equivalent lookup results. |
| FR-MAN-003 **[changed]** | Each file version shall have an immutable manifest containing path identity, metadata, logical length, ordered segment references (logical facts only, per FR-ARCH-010), parent-version reference where known, and a whole-file verification hash. | Manifest bytes are unchanged by any maintenance operation. |
| FR-MAN-004 | Trees and snapshots shall reference file-version manifests through immutable sharded tree objects. No snapshot shall require a monolithic repository-wide manifest. | No single manifest's size grows with repository or history size. |
| FR-MAN-005 | The catalogue shall resolve a path within a snapshot without scanning unrelated snapshots, trees, blobs, or records. | Resolution meets the NFR-PERF-004 latency target at the stated scale. |
| FR-MAN-006 **[amended]** | The catalogue shall resolve a content identifier within its segmentation profile, dedup trust domain, and **writer attribution** to determine whether a reusable segment exists. Writer attribution shall be recoverable from index delta `writer_id` during a rebuild. | Lookup meets the NFR-PERF-010 target. After a catalogue rebuild, `device` mode still identifies which segments this device wrote. |
| FR-MAN-007 | Every sealed blob shall include an authenticated recovery footer listing each record's object identifier, physical offset, stored length, logical length, and encoding profiles. | Forensic rebuild reconstructs all index entries from footers alone. |
| FR-MAN-008 **[changed]** | Index deltas shall be immutable and published only after their blobs are durable. Each delta shall carry `(writer_id, sequence, predecessor_delta_id)` with strictly increasing, gapless per-writer sequence. Checkpoints shall enumerate the exact delta IDs they subsume and the per-writer high-water sequence. | A reader detects a missing sequence number rather than assuming completeness. A delta above a checkpoint's watermark is applied even when listing omits it. |
| FR-MAN-013 **[amended]** | Two checkpoints published at the same generation shall both be retained and both applied. Convergence shall rest on explicit precedence, not on commutativity. | Applying either order, or both, yields identical catalogue state — including when one delta relocates an object identifier another delta already mapped. |
| FR-MAN-015 **[new]** | Every index entry shall carry the generation at which it was published, and shall declare whether it is an insertion or a **supersession**. For a given object identifier the highest generation shall win, with a documented deterministic tie-break. | After compaction relocates an object, a reader applying the pre-compaction delta last still resolves to the new location, never to the tombstoned blob. |
| FR-MAN-016 **[new]** | A writer that skips a journal sequence shall publish a signed **void delta** at that number. Readers shall treat a gap as unresolved until the delta or its void record appears, and shall surface it as a damage finding after a bounded number of generations rather than blocking. | A writer that crashes between preparing and publishing a delta does not permanently block readers. Silence is never interpreted as an empty delta. |
| FR-MAN-017 **[new]** | A delta shall be retired only when named by a checkpoint that no live checkpoint at or above its generation contradicts. Retirement shall use tombstone-and-grace. | With concurrent checkpoints naming different delta sets, no reader loses index entries for a delta retired on another checkpoint's authority. |
| FR-MAN-009 | The engine shall support normal rebuild (checkpoint plus deltas) and forensic rebuild (blob footers plus snapshot roots). | Both succeed; forensic rebuild succeeds after every index object is deleted. |
| FR-MAN-010 | Listing and restore shall become available incrementally during rebuild, as soon as the required dependency graph is known. | A snapshot restores before full repository rebuild completes. |
| FR-MAN-011 | Rebuild shall verify signatures, authenticated metadata, record bounds, duplicate and conflicting mappings, generation ordering, and references to missing blobs. | Each injected fault class is detected and named. |
| FR-MAN-012 | The engine shall distinguish catalogue corruption, missing index objects, missing blobs, corrupt records, and unreachable orphans, reporting which snapshots and file versions are affected. | Each fault class produces a distinct report naming the affected scope. |
| FR-MAN-014 **[new]** | Rebuild shall never rewrite or repair repository objects. | A rebuild run leaves every repository object byte-identical. |

## Deduplication trust

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-DED-001 **[new]** | The repository shall support dedup trust domains `device`, `repository`, and `repository-unverified`. | Each is selectable and recorded in the policy manifest. |
| FR-DED-002 **[amended]** | `repository` shall be the default. In a single-writer repository it shall behave identically to `device` at no additional cost. `device` shall remain available as a hardened opt-in. | A fresh single-device repository performs no verification reads. A multi-device repository deduplicates across devices with verify-on-reuse. |
| FR-DED-003 **[amended]** | In `repository`, a segment written by another writer shall be fetched, decrypted, and its content identifier confirmed before being referenced. | A segment whose stored plaintext does not match its claimed content identifier is never referenced, and the mismatch is reported as a damage finding naming the object. Verification outcomes are catalogue state and are **not** required to survive a rebuild. |
| FR-DED-004 **[new]** | `repository-unverified` shall require explicit acknowledgement recording that a faulty or hostile writer can corrupt other devices' backups. | It cannot be enabled without the acknowledgement. |

## Snapshots

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-SNP-001 **[amended]** | A snapshot shall be committed to a replica only after every object it references is durable **in that replica**. Commit is per-replica; replication to other destinations is independent state. | For a staging set, a destination being offline delays policy compliance but does not prevent local commit. For a direct-ship set ([ADR-0046](../adr/0046-direct-to-destination-publication.md)) there is no local replica to commit to: the snapshot commits at each destination that completed the run, and FR-DEST-015 governs the case where none could. |
| FR-SNP-002 | File deletion shall create new snapshot state and shall not directly delete older file versions or segment records. | Prior versions remain restorable after a deletion snapshot. |
| FR-SNP-003 **[new]** | Each `(snapshot, destination)` pair shall carry independent replication status: `pending`, `replicating`, `durable`, `verified`, `degraded`. | Status is queryable per destination and drives policy evaluation. |
| FR-SNP-004 **[amended]** | A write-intent record naming the blobs a job will create shall be durable **before** those blobs are uploaded, and retired when the work completes. This shall apply to **every** component that creates a blob, including the garbage collector during compaction. | No blob is uploaded without covering intent, verified for backup writers and collectors alike. Garbage collection never deletes an intent-covered blob. |
| FR-SNP-005 **[new]** | An intent shall expire only when **both** the repository has advanced past its `expiry_generation` **and** its writer-declared `declared_max_duration` has elapsed with a configured skew margin. | A slow writer's intent is not expired by other writers' activity advancing generations. An audited administrative force-expire exists. |
| FR-SNP-006 **[new]** | Blob identifiers shall be writer-allocated and opaque, not content-derived, so a writer can name them in an intent before creating them. | A blob identifier is allocatable before the blob is sealed. Record identifiers remain content-derived and keyed. |
| FR-SNP-007 **[new]** | Each replica shall declare a failure domain (`same-volume`, `same-machine`, `same-site`, `independent`). A snapshot shall be reported `protected` only when at least one replica outside the source's failure domain holds it; one held only within the source's domain is `captured`. | A repository configured on the source volume reports `captured`, never `protected`. First-run warns when the only destination shares a failure domain with the source. |
| FR-SNP-008 **[new]** | A backup set shall capture one or more source folders into a single snapshot. With several, each folder shall appear at the snapshot root as a directory named by a label persisted in configuration, capture rules shall be evaluated against label-prefixed subjects, and a backup shall refuse — recoverably, naming every missing folder — rather than capture with any folder absent. A single-folder set's snapshot shall be byte-identical to the pre-multi-root shape. | A two-folder set publishes one snapshot whose top level is the two labels in raw-byte order and restores as `<output>/<label>/…`; a label-prefixed exclude prunes only its own folder's subtree; a run with one folder unmounted records a recoverable failure naming it and publishes nothing; a one-folder set round-trips with no synthetic root. |

## Restore

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-RST-001 | Restore shall support selecting device, backup set, snapshot or time, path, file version, and destination. | Each selector is exercised end to end. |
| FR-RST-002 | Restore shall verify each segment after decryption and the complete reconstructed file before reporting success. | A corrupted segment fails the restore rather than producing a corrupt file. |
| FR-RST-003 **[new]** | A restore plan shall be produced before transfer, reporting required objects, replicas, logical and physical size, target conflicts, path and case collisions, unpreservable metadata, free space, and required privileges. | A collision or space shortfall is reported before any byte is written. |
| FR-RST-004 **[new]** | Restore shall produce a machine-readable receipt listing every file restored, every degraded attribute, and every failure. | The receipt accounts for every file in the plan. |
| FR-RST-005 **[new]** | Restore shall never report success when any required file failed. | A partial restore reports failure and names what failed. |
| FR-RST-006 **[new]** | Restore of historical content shall default to a quarantine path rather than the original location. | In-place restore requires an explicit choice. |

## Recovery kit

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-KIT-001 **[new]** | The kit shall contain kit format version, minimum recovery-tool version, repository ID, format profile, **wrapped** repository master key, KDF parameters, destination descriptors, issuing device public identity, issue timestamp, embedded instructions, and an integrity checksum. | A conformance fixture kit parses and opens a fixture repository. |
| FR-KIT-002 **[new]** | The kit shall never contain the passphrase, store credentials, or the device private key. | Format validation rejects a kit containing any of them. |
| FR-KIT-003 **[new]** | The kit shall be produced in printable (QR plus checksummed transcribable text) and machine-readable representations with identical content. | A hand-transcribed printable kit opens the repository; a transcription error is detected by the checksum. |
| FR-KIT-004 **[new]** | Kit generation shall occur during first-run setup and require explicit confirmation that it has been saved before setup completes. | Setup cannot complete without the confirmation. |
| FR-KIT-005 **[new]** | Kit status — never generated, saved, stale — shall be surfaced continuously. | Changing destinations marks the kit stale. |
| FR-KIT-006 **[new]** | A recovery drill restoring a file using only the kit shall be a supported, prompted workflow. | The drill runs without the catalogue or durable local state. |

## Write-only repositories

A format-v2 repository ([ADR-0042](../adr/0042-write-only-repositories.md)) severs writing from reading: the service seals file contents to an asymmetric public key and holds nothing that opens them.

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-WOR-001 **[new]** | A repository may be created write-only (format v2): every key derives from one user passphrase via a memory-hard KDF and one-way domains; file contents are sealed to the derived X25519 public key; the service holds only the write bundle and can add to history but never read file contents back. | A service holding a v2 set's complete state cannot produce a byte of restored file content; backup, browse, plan, trim and replication all succeed without the passphrase. |
| FR-WOR-002 **[new]** | The passphrase shall be entered only at setup, at adoption of an existing repository onto a new service instance, and at restore. It shall never be persisted anywhere, and shall never transit any channel: derivation runs in the admin client, and only envelopes sealed to the service's published recipient key cross to the service. | No durable state on any machine contains the passphrase; the command surface carries only sealed envelopes on the two named verbs. |
| FR-WOR-003 **[new]** | The structure plane — metadata records, blob footers and record tables — shall remain readable to the write-bundle holder, so browsing, planning, dedup bookkeeping, retention and structural verification work without the passphrase. | Every blob's record table opens under the write bundle while its record payloads do not; the restore wizard reaches its review step without a grant. |
| FR-WOR-004 **[new]** | Restoring from a v2 repository shall require re-deriving the private key from the passphrase; the resulting grant shall live only in memory, bounded to a restore-source handle, and be zeroed on close or idle expiry. | A restore without a grant is refused naming the grant; after close or expiry the service again cannot produce content. |
| FR-WOR-005 **[new]** | Loss of the passphrase shall be unrecoverable by design, and the passphrase shall not be changeable for a v2 repository; setup shall require an explicit acknowledgement of both before completing. | Setup cannot complete without the typed acknowledgement; no verb offers a v2 passphrase change. |

## Destinations and fan-out

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-DEST-001 **[new]** | A backup set shall declare one or more named destinations, referencing declarations made once at the top level of the client configuration. None of them need be local: a set whose only destination is a peer or a removable drive is valid. A set with no destinations is rejected at configuration time with a stated reason. | Configuration with a peer-only set validates; configuration with a destination-less set is refused naming the set. |
| FR-DEST-002 **[amended]** | Each snapshot shall be **packaged exactly once** — scanned, split, compressed and encrypted one time on the agent — however many destinations receive it. A staging set publishes into its staging archive and fans out to destinations as immutable-object copies ([ADR-0034](../adr/0034-hub-and-spoke-destinations.md)); a direct-ship set ships each sealed object from the packaging spool to every in-scope destination directly ([ADR-0046](../adr/0046-direct-to-destination-publication.md)). Either way, no destination holds an archive whose journal references objects deliberately absent from it. | Two destinations of one set each hold a whole, independently restorable repository with one snapshot history; each restores independently with the recovery tool; a second backup re-reads and re-packages nothing a destination already holds. |
| FR-DEST-003 **[amended]** | An unavailable destination shall not delay or fail a capture **that has somewhere to land** — for a staging set that is always; for a direct-ship set, whenever at least one in-scope destination is reachable (the zero-reachable case is FR-DEST-015's stated refusal). The gap shall be recorded per `(set, destination)` and closed automatically when the destination returns, without operator action. | A backup with one destination offline completes; the destination catches up on its next appearance with no command issued; a direct-ship destination dropped mid-run is named in the ledger and healed by the next catch-up. |
| FR-DEST-004 **[amended]** | Per-`(set, destination)` sync state — last attempt, last success, how far behind, and the failure class of the last error — shall be durable across service restarts and reported per destination, never summarised into one flag. Every state below in-sync shall carry its cause — the ledger's own recorded words where any exist, and a stated cause for a demotion the status derivation itself decides (a destination behind the set's last completed backup, an owed seed, a pair never synced) — as prose in the row's detail and warning, and as a machine cause code with the compared last-completed timestamp on the wire, so a self-healing catch-up window is distinguishable from a fault without parsing prose ([ADR-0050](../adr/0050-completed-run-record-and-drill-down.md)) **[amended]**. For exactly that window — a destination behind only because a newer backup awaits its next sync pass, with a recorded prior success — the set shall keep the protection badge its held copy earns; `degraded` shall require a reported fault, an unreachable or failing destination, a never-synced pair, or an owed seed **[amended]**. | After a restart, `status` still names which destination is behind and why. A destination read behind minutes after a successful backup says it is catching up to that run and heals on the next sync pass — never a bare "behind" — and the set keeps its `captured`/`protected` badge through the window. |
| FR-DEST-005 **[new]** | Destination kinds `local-path` and `peer` shall be operational. Kinds `s3`, `azure-blob`, and `dropbox` shall be accepted by configuration validation and refused at runtime as a stated incapacity, distinct from failure. | A configured cloud destination reports "not yet supported", not `degraded`; it appears in the status matrix as such. |
| FR-DEST-006 **[new]** | Destination addresses — paths, peer endpoints and fingerprints — shall live only in the local configuration. Pairing grants shall hold no endpoint; the repository shall hold no destination list. | A grant round-trips with no address field; a repository fixture contains no endpoint bytes. |
| FR-DEST-007 **[new]** | Removing a destination shall warn what remains there and that the hub stops managing it — the data at the destination is not deleted by the removal. | Removal names the sets affected and the copies left behind; the destination's archive is untouched. |
| FR-DEST-008 **[new]** | Either side of a peering may end it unilaterally. The ending shall produce a durable notice on both sides — delivered when reachable, inferred from refusal otherwise — surfaced until acknowledged. | Terminating while the peer is offline still surfaces a notice at that peer's next dial; both households see a warning that survives restart. |
| FR-DEST-009 **[new]** | A destination's declared address shall be checked for the defects that can be found without touching the world — a relative local path, a fingerprint that is not one, an endpoint that is not `host:port` — and each defect reported wherever the destination is reported. The check shall never refuse a configuration: a defect in one destination shall not stop other sets backing up or stop status answering. A destination shall additionally be probeable on demand, confirming it could accept a backup without sending one, and a probe shall record its failures but never a success. | A configuration carrying a mistyped endpoint loads, every other set keeps running, and status names the defect; probing a detached drive reports it unavailable and probing a live peer establishes a session, leaves nothing there, and writes no last-success. |
| FR-DEST-010 **[new]** | Where a quota bounds a destination, the destination shall report the bytes it can still accept, and the source shall warn before a push runs into that ceiling rather than only when one does. An absent report shall mean "not stated", never "no room". A copy to a local path shall not begin when the destination volume's free space is under the floor the hub leaves for the machine that owns it, and shall be recorded as a gap that closes itself rather than as a fault. | A peer whose loan is nearly spent produces a warning while its syncs still succeed; a destination under no quota produces none; a volume under the floor is recorded unavailable and resumes unbidden once space is freed. |
| FR-DEST-011 **[new]** | A local-path destination shall not lie at or under any backup set's source root — the backup would capture its own archive — unless that set's exclude rules provably fence the folder off, judged with the same rule evaluation the scanner walks under. The same shall hold for the service's own state and archives directories inside a source root. The refusal shall happen at configuration edit, naming both paths, and never on the configuration load path: an installation already carrying the layout keeps loading, and the edit that would keep it is what is refused. The check shall be lexical and never touch the filesystem. | Saving a set whose root contains a declared destination is refused naming both paths with the file untouched; the same layout with the destination excluded saves; the rule edit that stops excluding it is refused; a sibling folder sharing a name prefix is accepted; the editor's draft validation reports the same finding as a defect. |
| FR-DEST-012 **[new]** | A local-path destination's address shall be stored absolute: a relative path declared at the boundary shall be resolved against the service's working directory at declaration time and the resolution said back to the declarer. A stored relative path that bypassed the boundary shall be refused by whatever ships to it — fan-out or ship sink — as a defect needing a person, never resolved at copy time. | Declaring a relative path stores its absolute form and the reply names it; a hand-edited relative path is recorded `failed` naming the defect, and nothing is written relative to the process working directory. |
| FR-DEST-013 **[new]** | A backup set may be flagged direct-ship ([ADR-0046](../adr/0046-direct-to-destination-publication.md)): its content is written to its destinations directly, and the agent's disk holds only the set's metadata store and a bounded in-flight spool — no staging archive, no whole-archive copy of the backup, nothing cached beyond a sealed object's last destination acknowledgement. Reads route to whoever holds the bytes: metadata locally, blob content from the first destination holding the key in priority order, listings as the union across destinations. | A direct-ship capture populates every reachable destination with an independently restorable repository while the agent's state directory gains metadata only; restore, destination verification and the retention traversal answer through the destinations with no local content. |
| FR-DEST-014 **[new]** | A destination shall be recorded as holding a full backup — its baseline — and one without a baseline shall be **skipped by incremental runs** (an incremental would hand it a snapshot without its closure) and **seeded by catch-up instead**. The pair owed its seed shall be marked (`needs_full`), and both facts shall be reported on the destination's status row, distinguishable from a bare "behind". | A destination gained by an existing set is marked owed its seed and queued for one immediately; incrementals skip it until the seed completes; the status matrix says when each destination's baseline completed and whether it is still owed one, and a pair that already holds a baseline is never re-marked. |
| FR-DEST-015 **[amended]** | A direct-ship capture with **no reachable in-scope destination** shall refuse as a stated, recoverable failure — there is nowhere to write, and pretending otherwise would fabricate protection — and the next scheduled pass shall retry without operator action. This is [ADR-0046](../adr/0046-direct-to-destination-publication.md) §4's deliberately accepted trade: the staging model's capture-is-unconditional property is given up for direct-ship sets. The storage shape shall be operable, not a config-file secret: carried on the set descriptor (contract 1.23, null preserving), offered by the console, refused while the set has a live run, effective without a service restart, and seeded immediately on a flip. A **new set referencing a local-path destination shall default to direct-ship** (a peer-only set stays staging until the sink serves peers), a direct-ship set shall be refused without a local-path destination, and retention's sweep shall reach the destinations — a delete the replication gate has licensed fans to every reachable destination, the metadata store last **[amended]**. | With every destination detached, the run records a recoverable failure naming the condition and commits nothing; reattaching a destination lets the next pass capture unbidden. Flipping a staging set on from the console migrates it in the same process and the catch-up seeds without a pass; a new local-path set is born direct-ship; after tombstone, grace and sweep, the destination replica holds its policy's keep-set and restores from it alone. |
| FR-DEST-016 **[new]** | A migrated direct-ship set's staging archive shall be deleted only by an explicit retirement command, refused while the archive holds any object absent from the union of the set's destinations — never silently, never automatically. Retirement shall resolve the standing notice that announced it. | Retiring immediately after the flip is refused counting the objects that have not reached any destination; after catch-up seeds them, retirement deletes the archive, resolves the notice, and prior history restores from the destinations alone. |

## Replication and verification

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-REP-001 **[changed]** | Repositories shall replicate between instances by exchanging immutable blobs, manifests, snapshots, and index generations. Replication state is tracked per `(snapshot, destination)` and is independent of commit. | A destination catching up after an outage advances only replication state. |
| FR-REP-002 | Azure Blob Storage and Amazon S3/S3-compatible stores shall be supported through the common object-store abstraction. | Both pass the shared contract suite. |
| FR-REP-003 | Transfer shall resume at verified boundaries and never expose a partially written blob as committed. | Interruption mid-transfer leaves no visible partial object. |
| FR-REP-004 **[new]** | Peers shall negotiate a common protocol feature set at connection. A peer unable to satisfy the other's required features shall refuse with a stated reason. | A version-skew pair refuses cleanly rather than failing mid-transfer. |
| FR-VER-001 **[new]** | Destination verification shall use a keyed random-range challenge whose response cannot be precomputed, cached, or replayed. | A destination that discarded the data fails, even having answered a prior challenge for the same blob. |
| FR-VER-002 **[new]** | Verification shall sample blobs per interval, weighted towards those longest unverified, always covering the most recent snapshot's dependencies. | Coverage and challenge age are reported per destination. |
| FR-VER-003 **[new]** | Verification status shall be reported as coverage and age, never as a bare boolean. | No UI surface presents "verified" without both. |
| FR-VER-004 **[new]** | Full on-demand verification shall be available and shall run before a recovery drill. | It completes and reports per-object results. |
| FR-VER-005 **[new]** | A verification failure shall mark the affected `(snapshot, destination)` `degraded` and raise a warning requiring action. | Status changes and the warning appears. |
| FR-VER-006 **[new]** | A destination shall be verifiable. One that cannot answer challenges shall be refused rather than replicated to, unless the configuration explicitly acknowledges keeping it unproven; the acknowledgement shall not be available to a destination the source can read back itself. An unproven destination shall never report `verified` and shall never license reclaiming the source's last local copy. | A peer that does not offer verification is refused with a stated reason and holds nothing; the acknowledgement is a value that cannot be set by accident, and is refused outright on a local path; an unproven destination never licenses reclaiming a last copy — neither the staging trim's gate nor a direct-ship retirement or convergence — and the retention report names it and why. |

## Retention and garbage collection

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-GC-001 **[new]** | Retention shall select protected snapshots and delete nothing. | A retention change reclaims no space until collection runs. |
| FR-GC-002 **[new]** | Collection shall mark from a generation cut-off over snapshots protected as of that generation. | Objects published after the cut-off are out of scope. |
| FR-GC-003 **[amended]** | Every blob covered by an unretired write intent shall be treated as reachable, including intents published by a collector for its own compaction output. | Collection concurrent with an in-flight backup deletes none of its blobs. Two concurrent collectors do not delete each other's replacement blobs. |
| FR-GC-004 **[amended]** | Blob compaction shall republish index entries only, as supersessions per FR-MAN-015, and shall modify no manifest, tree, or snapshot. | Manifest bytes are unchanged after compaction; all references still resolve regardless of delta application order. |
| FR-GC-005 **[new]** | A dry-run report shall be produced before any destructive pass, stating what would be deleted and compacted, space reclaimed, and which snapshots were treated as protected. | The report is generated and no object is deleted. |
| FR-GC-006 **[new]** | Deletion shall follow tombstoning, a configurable grace period, and pre-delete revalidation, in bounded batches. | Interruption at any step leaves every published snapshot recoverable. |
| FR-GC-007 **[new]** | Destination-side retention floors shall not be reducible by a source device. | A source request to reduce below the floor is refused and audited. |
| FR-GC-008 **[new]** | Retention reduction and bulk snapshot deletion shall require stronger authorisation than ordinary backup, and shall produce signed audit records. | Both are recorded and attributable. |
| FR-GC-009 **[amended]** | Retention shall not expire a snapshot that has not reached the destinations its own policy requires, unless a configured deferral bound is exceeded — at which point the resulting history gap shall be raised as a warning requiring action. Reclaiming the source's last copy of an object shall rest on a destination's **proof** of possession, never on a record of what was sent to it. | A destination offline beyond the local retention window does not cause history to be lost from every replica silently. A destination with a current sync record but no covering proof does not license the deletion. |
| FR-GC-010 **[new]** | Retention policy shall be declared per backup set, with optional per-destination overrides. The hub computes each destination's keep-set — only the hub can read manifests — and a destination deletes only what the hub instructs, bounded below by its own granted retention floor: an instruction that would breach the floor is refused with a stated reason. | Two destinations of one set hold different snapshot ranges under different overrides, each restorable; a floor-breaching instruction is refused and the refusal is visible at the hub. |

## Service and clients

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-SVC-001 **[new]** | The engine shall run as a service, and every user interface shall be a client of it over one command contract. | The CLI, a desktop shell, and a web front end perform the same operation through the same contract; no front end opens the repository except the CLI's direct mode (FR-SVC-002). |
| FR-SVC-002 **[new]** | Exactly one process shall hold a device's writer role at a time, enforced by an exclusive lock on the state directory. A process that cannot acquire it and finds no service to call shall refuse with a stated reason naming the holder. | Two concurrent writers cannot be created: the second fails with a message, never proceeds. Killing the holder releases the lock without manual cleanup. |
| FR-SVC-003 **[new]** | The local binding shall always be present and authenticated by the operating system. The remote binding shall be absent until explicitly enabled and shall name the interface it binds. | A default install listens on no port. With the remote binding enabled, an unpaired client is refused. |
| FR-SVC-004 **[new]** | Remote clients shall be authenticated by paired device identity pinned on approval, revocable at the service. A changed identity shall be a hard failure requiring re-approval. | Pairing requires approval on both sides; a substituted identity is refused rather than prompted; revocation at the service ends access immediately. |
| FR-SVC-005 **[new]** | A remote client shall receive control, status, and progress, and shall not receive file content unless that capability is separately and explicitly enabled. | A restore commanded remotely writes on the service's machine; no plaintext crosses the remote binding by default. |
| FR-SVC-006 **[amended]** | The service shall emit per-job progress carrying job identity, the [10 §3](../architecture/10-observability.md#3-job-state-machine) state, and counts of files and bytes. A backup shall first count what it will process — the same rules the capture judges by, no content read — and every report thereafter shall carry that plan (total files and total bytes), sufficient for a client to derive a percentage complete and a time estimate; the counting tally itself shall be reported while it runs **[amended]**. A subscriber arriving mid-run shall receive each live job's latest report at once, a subscriber that disconnects shall release its subscription immediately, and per-report work shall be bounded and coalesced so an unwatched service pays no per-file aggregation ([ADR-0048](../adr/0048-determinate-backup-progress.md)) **[amended]**. Each report may name the file currently being processed — to the feed's authenticated audience only, riding the coalesced cadence, never a per-file ledger ([ADR-0050](../adr/0050-completed-run-record-and-drill-down.md)) **[amended]**. | A running job reports states beyond `Scanning`; a client can distinguish a working job from a stalled one without reading engine files; a clean run's terminal report shows its plan equal to its processed count, and a rule-excluded file is absent from the plan; a console attaching mid-run renders the meter from the replayed snapshot without waiting for the next file; a client that hangs up mid-watch is unsubscribed without another event being produced; a watcher of a long run sees which file it is on. |
| FR-SVC-007 **[new]** | Client and service at incompatible contract versions shall refuse to proceed with a message naming both versions. | Neither a blank UI nor a silent partial success; a console managing several services degrades per service rather than refusing to start. |
| FR-SVC-008 **[new]** | All four installation topologies shall be supported by one service implementation: all-in-one, service-only, a console managing several services, and a client alone. | Each topology is installable and functional; a service with no front end installed backs up unattended, and an unreachable console never stops it. |
| FR-SVC-009 **[new]** | A material change to a backup set's source folders or capture rules shall be answered with what changed and shall trigger a rescan comparing the source against the set's latest snapshot, surfacing new, updated, moved, deleted, and no-longer-included files as a durable notice until a backup for the set completes. The same comparison shall be commandable on demand with exact counts and bounded path samples. | Editing a set's root or rules raises one per-set notice naming the counts, refreshed by later edits and resolved by the next completed backup; a file the rules stopped capturing is reported apart from a file the disk lost; the preview verb answers a draft's rules before anything is saved; the console applies a material edit only through a two-step confirmation that shows the comparison first. |
| FR-SVC-010 **[amended]** | The service shall record levelled, structured diagnostics for every engine and host operation, with the effective level configurable per category and changeable without a restart. A client shall be able to read recent records and, from the local binding, change the level; records leaving the machine shall carry no plaintext path and no correlatable repository identifier. At every start the service shall record the effective configuration it operates against — the resolved state and archives locations each with their provenance (flag, environment, or which default), the poll interval, the backup pool width, the binding posture, the passphrase posture as a word and never a secret, and each configured set and destination — sufficient to reconstruct its posture from the diagnostic log alone ([ADR-0049](../adr/0049-service-lifecycle-hygiene.md)) **[amended]**. | A backup, a restore and a failure each leave records naming the operation and its outcome; raising the level to `trace` and lowering it again takes effect on the next operation with the service still running; a paired remote client reads redacted records and is refused a level change; a start with a configured set leaves records naming the resolved directories with provenance, the pool width, and the set with its schedule and destinations. |
| FR-SVC-011 **[new]** | A service shall report whether its installation has been set up, and a client connecting to one that has not shall guide the operator through capturing the passphrase before anything else. The ceremony shall state, before the passphrase is entered, that it is the master key for the installation, that it is never stored and can never be changed, and that losing it makes every backup permanently unrecoverable, and it shall require an explicit acknowledgement of that consequence. The passphrase shall be refused if it falls below the enforced minimum length of sixteen, misses the composition rules — at least one uppercase letter, two digits, and one special character — or assesses as weak **[amended]**. | A service with no passphrase and no provisioned set reports `setup_required`, and a console shows the ceremony in place of its normal views; setup cannot proceed without the acknowledgement, without matching entries, or with a passphrase below the floor or missing a composition rule — each unmet rule named; a second setup is refused; after setup a new backup set's repository — its staging archive, or a direct-ship set's metadata store and destinations — is created write-only and backs up with no passphrase in the service's environment. |
| FR-SVC-012 **[amended]** | The service shall run a configurable number of backups concurrently — an operator-set pool width of 1 to 5, defaulting to 2 ([ADR-0047](../adr/0047-backup-pool-and-priorities.md)) — while keeping one run per set at a time **through every door that queues a run**: the scheduled pass, a manual trigger, and the first backup a saved set queues shall all be refused a second concurrent run of one set, atomically, and a refused trigger shall answer with the active run rather than an error **[amended]**. The scheduler shall keep evaluating due-ness while transfers run: a long destination copy shall never stop scheduled backups being considered. | Two sets back up at once on a width-2 pool while a third waits; a set with a run in flight is reported already-running, never double-queued — a manual trigger while the set's run is queued or running answers `job_accepted` naming the active job, begins no second journal row, and simultaneous triggers begin exactly one; scheduled incrementals hold their cadence during an hours-long transfer; a width outside 1..5 is refused at validation and answered with the default on the load path. |
| FR-SVC-013 **[new]** | Backup sets and destinations shall carry an optional integer priority, and waiting work shall be ordered by initiation, then priority, then arrival: a user-initiated job outranks any priority, a higher priority wins among work of the same initiation, and arrival breaks ties so nothing starves. A backup ships to its destinations in priority order. | Among queued scheduled backups the higher-priority set runs first; a user-initiated run jumps every scheduled one regardless of priority; two equal-priority jobs run in arrival order. |
| FR-SVC-014 **[new]** | When every pool slot is busy and a strictly higher-ranked backup arrives, the lowest-ranked running backup that can yield shall be **suspended at a file boundary** — its in-memory state held, its slot freed — and shall **resume where it stopped**, not restart, when a slot frees; a freed slot resumes suspended work before starting new work of equal standing. Suspension shall be bounded: a run paused past a configured age shall self-cancel to the interruption-safe re-run path, and shutdown shall degrade a suspended run the same way. The suspended state shall be visible as a live, non-terminal job state. | The incomer runs while the preempted backup is suspended, and the preempted backup then completes committing one whole snapshot with nothing re-scanned; a client awaiting the job keeps waiting through the suspension; shutdown while suspended cancels cleanly and the next run publishes intact. |
| FR-SVC-015 **[new]** | Saving a new backup set shall queue its first backup immediately — a person clicking Save is asking for a backup, not a schedule entry — and the reply shall name the queued job. A set gaining a destination shall mark the pair owed its full copy (FR-DEST-014) and queue that destination's seed immediately. | A new set's upsert reply names its queued first backup and the destination populates without waiting for a schedule; a gained destination begins seeding without operator action. |
| FR-SVC-016 **[new]** | Every process of the installation — the service, the web console, and the CLI — shall resolve the same default state location when none is named: the machine-wide data directory (`%ProgramData%\FallbackPlan`, `/var/lib/fallbackplan`, `/Library/Application Support/FallbackPlan`), falling back to the user profile only where that cannot be created, overridable by environment variable and then by the path flags. A bare service invocation shall start on that installation, a path-less console or CLI verb shall connect to it, and an unusable path (default or named) shall be refused with a stated reason, never a stack trace. | `fallbackplan-agent` with no arguments starts the service; `fallbackplan-web` with no arguments connects to it; a CLI verb naming no repository is answered by that service with no passphrase; the environment overrides redirect a whole session together; a state directory that cannot be created or opened is refused with a message naming the problem. |
| FR-SVC-017 **[new]** | The service shall reconcile its job journal at start: no record shall claim to be running in a process that is not running it — unfinished rows shall settle as recoverable failures with a durable notice raised. Cancelling a run whose record is unfinished but which is no longer live shall settle the record rather than refuse, and deleting a backup set shall defer only to runs the scheduler is actually running. An owner shall be able to command a service restart from the console and the CLI — an in-process recycle, identical on every platform — refused to operators by name, refused from the remote binding, refused before setup, and refused where no host can recycle ([ADR-0049](../adr/0049-service-lifecycle-hygiene.md)). | A journal carrying a mid-run row from a dead process starts with the row settled and one notice; cancel on a stuck record acknowledges and settles it; a set with only an orphaned record deletes; the console shows the restart control to the owner alone behind a typed confirmation, the CLI verb is `restart`, and the shipped host recycles in the same process — two listens, no exit — with every session signed out. |
| FR-SVC-018 **[new]** | A settled run shall be able to say what it did. Its terminal numbers — files seen, done, reused and failed, bytes read and newly stored, and the counted plan — shall persist on its journal row at every terminal transition, failed and cancelled runs included, additively (a pre-existing row reads back with none, never as corrupt), while the journal remains sacrificial on [ADR-0027 §2](../adr/0027-services-scheduling-status-telemetry.md)'s terms. The details shall be served from the repository on demand: what the run changed against the set's previous snapshot (exact counts, bounded samples, agreeing with the snapshot browser's comparison by construction), and its capture failures — each path with its typed reason and the scanner's own words — from the error manifest. A run that committed no snapshot shall be refused those details by name. The job listing shall accept a bound, newest rows first ([ADR-0050](../adr/0050-completed-run-record-and-drill-down.md)). | Clicking a completed job in the console opens its report: counts, bytes, duration, capture status, with "what changed" and "failures" one click deeper and the snapshot browser beside them; `jobs <id> --changes --failures` answers the same from the CLI; a partial run's row carries the counts its detail string omits; a cancelled run's row records how far it got. |

## User accounts and sessions

These are about **who is acting**, not about which process may connect. The
channel checks are unchanged: the local binding stays authenticated by the
operating system ([T-16](../threat-model.md)) and the remote binding stays
authenticated by pinned device pairing ([T-20](../threat-model.md), FR-SVC-004).
A password is never a new way to reach a service —
[ADR-0045](../adr/0045-client-authentication.md) §2.

| ID | Requirement | Acceptance |
|----|-------------|-----------|
| FR-USR-001 **[amended]** | An installation shall hold named user accounts, the first captured during first-run setup before setup completes. A password shall be refused where it is chosen — creation and change, never login — unless it is at least ten characters with an uppercase letter, two digits and a special character; the setup ceremony shall additionally refuse a password equal to the installation passphrase, compared by hash so the passphrase is not held. A client acting against a service shall identify itself as one of those accounts before issuing any command other than reading the service's description or logging in. | A fresh installation cannot complete setup without a first account; a password missing any rule is refused naming it, at the store so every creation path answers identically; the ceremony's account step will not enable Create User for the passphrase itself; a second console connecting to a set-up service can render a login screen and nothing else until it authenticates; every other verb is refused by name with how to log in. |
| FR-USR-002 **[new]** | A password shall be stored only as a memory-hard one-way hash with a per-account salt and its parameters recorded beside it, in the service's own state and never in the repository metadata plane. No password and no hash shall appear in any log record, any command result, or any diagnostic. | The stored form does not reveal the password and does not verify a different one; changing the password changes the salt; a full backup, restore and diagnostics sweep contains neither the password nor its encoded hash anywhere. |
| FR-USR-003 **[new]** | A successful authentication shall mint a session bound to the connection, with an idle timeout and an absolute expiry, listable and revocable at the service, held only in the running process. A restart shall end every session. | One authentication serves a connection's lifetime rather than one command; an idle session stops working without a new one being needed elsewhere; restarting the service requires everyone to log in again, and no session survives on disk. |
| FR-USR-004 **[new]** | The first account shall be the owner: it shall not be deletable and shall not be lockable out, and initially only it may create or remove accounts. Every account shall carry a role, so that narrower rights can later be granted without a migration. | Deleting the owner is refused by name; a second account cannot create a third; the stored form of every account carries its role from the first release, and reading an account written before any narrower role existed does not fail. |
| FR-USR-005 **[new]** | Repeated authentication failures for an account shall impose an increasing bounded delay and shall be recorded at warning with the account named. Nothing shall lock. | Five wrong passwords take visibly longer than one and the delay stops growing at its cap; the correct password still works immediately afterwards; no sequence of failures by anyone can deny an account its own backups. |
| FR-USR-006 **[new]** | The service process itself and the CLI's direct mode shall be unaffected: scheduled work shall run with no person present, and a direct-mode invocation holding the installation passphrase shall authenticate itself. Automation shall name a password by environment variable, never on a command line. | Scheduled backups run on a machine where nobody is logged in; `--direct` works with only the passphrase; a password given as a command-line argument is refused, and the named-variable form succeeds. |
